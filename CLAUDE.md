# Libro app - agent & developer rules

Single source of truth for how this project is built. Applies to humans and AI agents alike.
If a decision here needs to change, change it here first, then in code.

## Product in one paragraph

"read more" is a calm, book-only social app for readers, starting from the Libro Club community (180+ readers in Slovakia). Users post to a shared feed, run timed reading sessions (others can see and join them), mark good / slow / skipped parts, and every finished book grows a **tree** shaped by how it was read. Finished trees form a forest on the profile. Slovak first, English and Ukrainian later.

It is NOT a dating app (people meet in groups of 3+, around books, in public places) and NOT an attention trap (no streak guilt, no ads based on reading data). Reading data stays private.

## Current scope

- Mobile app: Expo / React Native.
- Current focus: **backend MVP**, built as a modular monolith so new modules (Stripe, matching, ...) can be added without touching the core.

## Stack

| Piece | Choice |
|---|---|
| Backend framework | NestJS (TypeScript) |
| ORM | TypeORM 1.x (`typeorm@^1.1` + `@nestjs/typeorm@^12`, confirmed compatible), repository mode (`TypeOrmModule.forFeature` + `@InjectRepository`) |
| Database | PostgreSQL (with PostGIS, pgvector, `unaccent`, `pg_trgm` when needed) |
| Validation / DTOs | zod 4 schemas through Nest 12's built-in Standard Schema support (`@Body({ schema })`, global `StandardSchemaValidationPipe`); the same schemas feed OpenAPI (`@nestjs/swagger` 12) and can move to `packages/contracts` to be shared with the app |
| Auth | Own JWT: short-lived access JWT (`@nestjs/jwt`) + rotated opaque refresh tokens, argon2id passwords, `@nestjs/throttler`; provider ID tokens (Google) verified with `jose` (see [Auth](#auth), [Identity providers](#identity-providers)) |
| Mobile | Expo / React Native |
| Photo storage | `media` module behind the `FILE_STORAGE` port: local disk now, S3 compatible object storage later; `sharp` re-encodes to WebP without EXIF / GPS (see [Media](#media)) |
| Later | Redis (realtime presence, BullMQ queues, shared rate-limit storage), Stripe |
| Repo layout | Monorepo, pnpm workspaces + Turborepo: `apps/api`, `apps/mobile`, `packages/tree-engine`, `packages/contracts` |

Rejected and why (do not reopen without a new reason):
- **MongoDB** - data is relational (social graph, feed, sessions, groups, billing), needs FK integrity and transactions; GDPR deletes are harder without FKs; JSONB covers the document-shaped parts.
- **MySQL** - weaker geo, vector, full-text and JSON support.
- **Microservices** - not for MVP; module boundaries keep the option open.
- **Separate repos for API and app** - the tree engine and API types must be shared directly; separate repos would mean publishing and version-syncing packages.
- **Laravel / Symfony** - would lose shared TypeScript (tree engine, API types) with the app.
- **class-validator / class-transformer** - decorator DTO classes cannot be shared with the app as plain schemas; zod covers validation and OpenAPI natively on Nest 12.
- **Better Auth** - session-centric and owns its tables through its own adapters, outside our TypeORM repositories, migrations and module rules; own JWT keeps auth a normal module (own `auth` schema, repositories, domain events) and fits a mobile-only client with bearer tokens.
- **Passport** - an extra layer for what a single guard and `@nestjs/jwt` already do.
- **nestjs-zod** - no Nest 12 support (peer `@nestjs/common` up to 11), and Nest 12 + `@nestjs/swagger` 12 already do what it adds.

## Architecture: modular monolith

- One deployable backend, strict boundaries between modules.
- Each module owns its tables, ideally in its own Postgres schema (`auth`, `reading`, `feed`, ...).
- **No cross-module joins** and no direct access to another module's repositories or entities. Use the other module's public service interface.
- Modules talk through **domain events** (`BookFinished`, `SessionEnded`, `InsightAdded`, ...). A new module subscribes to events; the core does not know about it.
- Depend on abstractions (interfaces / injection tokens), not concrete classes from other modules.

### Modules

MVP:
- `auth` - accounts, login (email + Google; Apple later), linking provider identities to accounts, account deletion
- `identity-providers` - verifies provider ID tokens (Google now, Apple later); no tables, knows nothing about users
- `profiles` - handle, display name, bio, favourite genres, top 3 books, avatar, one-way following
- `books` - catalogue (e.g. Open Library import)
- `reading-sessions` - timer, checkpoints, marked parts (good / slow / skipped), joining sessions
- `tree` - deterministic tree engine
- `feed` - posts, likes, emoji reactions (the emoji-only comments), places; following and community feeds; the activity feed (Libro announcements, book updates, statuses)
- `reviews` - rating (1 to 5 stars) and optional review of a finished reading, visible to the reader's followers
- `encouragements` - insights (short thoughts of followers to a book being read) and congratulations on a finished book; they decorate the reader's tree
- `media` - photo uploads: WebP variants without metadata, swappable file storage, signed URLs

Later (design so they plug in via events and interfaces):
- `billing` - Stripe webhooks + entitlements
- `matching` - groups of 3+ based on read / liked books, never 1:1
- `realtime` - live sessions (WebSocket gateway)
- `search`, `ai`, `notifications`

### Domain events

In process, immediately, no outbox.

- **Delivery:** `publish` runs every handler in the same process and resolves after all of them finished. An event is lost if the process crashes or a handler fails; acceptable for the MVP. Moving to an outbox / queue later must not change the publisher or handler API.
- **Publish after commit:** publish only after the write has been committed, never from inside an open transaction, so handlers never see rolled-back data.
- **Definition:** `defineDomainEvent<Payload>('BookFinished', 1)` once, in the publishing module's public API; publisher and handlers use the same definition. Names are past tense PascalCase (`BookFinished`, `SessionEnded`).
- **Versioning:** every event has a `version` (starts at 1). A breaking payload change is a new version; the old one keeps being published while consumers exist. Handlers subscribe to one version (`BookFinished.v1`), so a v2 event never reaches a v1 handler.
- **Payload:** ids and facts only, never entities or personal data beyond what the consumer needs. Events are deeply immutable copies; payloads hold only plain objects, arrays and primitives (no `Date`, `Map`, `Set`, class instances or cycles).
- **Handlers:** `@OnDomainEvent(BookFinished)` on a provider method. A failing handler is logged (event, version, handler, stack) and neither fails the publisher nor stops other handlers. Handlers must stay fast; slow work goes to a queue later. Handlers live in singleton providers; the app refuses to start otherwise.
- **Transport:** only `src/events` touches `@nestjs/event-emitter`; everyone else injects `EVENT_BUS` (ESLint enforces it).

### Module conventions

Modules live in `apps/api/src/modules/<module>/`. The reference module is `books`; copy its layout:

```
index.ts             public entry: module class, public interface (token + interface), event definitions
<module>.module.ts
book-catalogue.ts    public interface other modules inject (BOOK_CATALOGUE + BookCatalogue)
events/              domain event definitions
domain/              plain types and rules, no framework code
application/         services, repository interfaces + tokens, ProblemExceptions
http/                controllers, zod request / response schemas
persistence/         entities, *.repository.ts, entity mappers
factories/ seeds/    typeorm-extension factories and seeders
```

- **Public entry only:** other modules and code outside `modules/` (e.g. `app.module.ts`) import a module only from its `index.ts`. It never exports entities, repositories or internal services. Platform code (`src/events`, `src/http`, `src/database`, `src/shared`, `src/config`) is free to import.
- **Database access only in repositories:** services depend on a repository interface + token (`WORK_REPOSITORY`). Only `persistence/*.repository.ts` (plus the module's own `seeds/`, `factories/`) may use `@InjectRepository` / `getRepositoryToken`, `DataSource`, `EntityManager`, `QueryRunner`, `Repository`, query builders, `.query()`, `.transaction()` or `.manager` (also through subpath, dynamic or computed access; `require()` is banned in modules). A multi-table write is one transaction inside the repository; the service publishes events after it returned.
- **Schema:** entities declare `schema: '<module>'` and name their constraints (`_pkey`, `_fkey`, `_key`, `_check`, `_idx`). Unique violations become a `ProblemException` in the repository (`isUniqueViolation` from `src/database`), so concurrent duplicates answer 409, not 500.
- **HTTP:** controllers map domain types to a response DTO, never return entities. Domain errors are `ProblemException` subclasses with an own `code` in `application/`.
- **Seeds and factories:** one deterministic factory per aggregate (`setSeederFactory`, overrides via `setMeta`), registered in `apps/api/test/support/seeder-factories.ts` for the per-test `factories` fixture. Seeders are idempotent.
- **Tests** live in `apps/api/test/modules/<module>/`: behaviour through HTTP, arranged data through factories.
- **User data and account deletion:** every module that stores anything of a user (a user id, or rows owned by one) handles `UserDeleted` v1 with an `@OnDomainEvent(UserDeleted)` handler that deletes all of it, idempotently, in its own repository (one transaction per module). Shared things (follows, later comments, reactions, likes, insights, congratulations, group memberships) are deleted, never anonymised. Extend the arranged account in `apps/api/test/modules/account-deletion/account-deletion.fixture.ts` with the new module's data; the generic scan test fails for a new table without arranged data of that user (unless it is listed, with a reason, in the test's `TABLES_WITHOUT_USER_DATA`) and for any trace left after the deletion (see [Account deletion](#account-deletion)).
- **ESLint enforces** the public entry rule (`eslint-plugin-boundaries`) and repository-only database access (`no-restricted-imports` / `no-restricted-syntax`); `apps/api/test/lint/` proves both.

## The tree rule

- **Never store a picture of the tree.** Store what the reader did (sessions, marked parts, insights from friends, congratulations) and compute the tree from that data every time.
- The same reading data must always produce the same tree (deterministic, no randomness without a seed derived from the data).
- Faking reading must be burdensome: trees come from many real sessions with checkpoints, not from a single action.
- The engine is a pure function, shareable between backend (validation, anti-cheat) and the app (rendering, animation).
- **The engine is versioned.** Every tree records the `treeEngineVersion` it was computed with. Old algorithm versions stay available so finished trees never change shape. The API returns the engine version so the app knows which algorithm to render with.

## Tree engine

Package `packages/tree-engine` (`@libro/tree-engine`): zero runtime dependencies, no NestJS, no Node APIs, so the same code runs in Node and in Hermes / React Native. It exports its TypeScript source (`exports` -> `./src/index.ts`, relative imports with `.ts` extensions, `erasableSyntaxOnly`) and has no build step.

- **Consumers:** Metro, vitest and the API use the source directly. The API depends on it (`workspace:*`); `tsc` type-checks it as an external library (not emitted, no `rootDir` conflict; the API tsconfig enables `rewriteRelativeImportExtensions` so the `.ts` imports are accepted), the compiled API keeps the bare `@libro/tree-engine` import, and Node strips the types at runtime because the pnpm symlink resolves outside `node_modules` (Node never strips types inside `node_modules`). So the engine must keep erasable syntax only. Turbo's `transit` task makes the API's lint, typecheck and test caches depend on the engine's files; the dev container copies and mounts `packages/tree-engine/src`, and a production image must ship it next to the API `dist`.
- **API:** `computeTree(input, version?)` (default `LATEST_TREE_ENGINE_VERSION`), `TREE_ENGINE_VERSIONS` registry, `isTreeEngineVersion(value)` to narrow a stored version; an unknown version throws `UnknownTreeEngineVersionError`. The output carries `treeEngineVersion`.
- **Versioning:** each version lives in its own folder (`src/v1/`) with its own helpers (PRNG included) and is frozen once shipped. Any change to a version's output is a new folder (`src/v2/`) plus a registry entry; old folders are never edited. Golden snapshots (`test/__snapshots__/golden.test.ts.snap`) fail on any v1 output change; never update them for a shipped version.
- **Determinism:** the same input gives byte-identical output in every JS engine. Integer and fixed-point math only (`Math.floor`, `Math.imul`, `>>> 0`, per-mille ratios, rational saturation `x / (x + k)`); no `Math.sin` / `cos` / `exp` / `log` / `pow` / `sqrt` / `random`, no `**`, no `Date`, `Intl` or locale methods, no imports outside the package (ESLint enforces it in `packages/tree-engine/src`). Randomness is FNV-1a + MurmurHash3 finaliser over `seed/<purpose>/<ids>` feeding mulberry32. Every number in the output is an integer; the app does the trigonometry.
- **Input v1:** `{ seed (the reading id), finished, sessions: [{ activeSeconds, checkpoints: [{ page }], markedParts: [{ kind, fromPage, toPage }] }] (chronological), decorations: [{ id, kind: insight | congratulation | group_reading }] }`. Bad numbers (negative, `NaN`, infinite) count as `0`; nothing throws.
- **Counting rule:** a session counts only with at least 300 active seconds and at least 1 checkpoint; other sessions (and their marked parts) are ignored, never rejected. A session contributes at most 7200 seconds. Growth is `1000 * s / (s + 21600)` (`s` = counted seconds), so it saturates below 1000; stage `seed` (no counted session), `sapling` (< 250), `young` (< 600), `mature`.
- **Mapping:** reading time -> trunk height and thickness and branch length; each of the first 40 counted sessions -> one branch (`b<n>`, attached to the trunk or an earlier limb); good parts -> flowers; slow parts -> extra leaves; skipped parts -> thin bare twigs (`b<n>.t<k>`); finishing -> fruits. Slow and skipped parts only add, they never shrink the tree. Longer marked parts give bigger flowers, more leaves and longer twigs. Sessions after the 40th hang their leaves, flowers and twigs on branch `n % 40`.
- **Per-branch budgets:** every branch has fixed budgets, filled in session order: 6 base leaves (`b<n>.l<k>`), 6 slow-part leaves (`b<n>.s<k>`), 3 flowers, 2 twigs. Marked parts on one branch can never evict anything on another branch, and slow parts never evict base leaves. Counting looks at no more than 6 parts of each kind per session and stops allocating once a budget is full, so huge inputs stay cheap.
- **Growth continuity:** branch `n` and everything on it are derived from session `n` and the seed, so a new session keeps every earlier id, parent, position and angle; lengths, thickness and sizes only grow.
- **Fruits and decorations:** each one is placed from the seed and its own key alone (fruit index or decoration id): its position is fixed, and its branch is chosen by rendezvous hashing over the branches (the trunk while there are none). A growing tree only ever moves one onto a newly added branch; adding or removing a decoration never moves the others. Decorations sit on top and never change the shape; at most 100.
- **Output v1:** `{ treeEngineVersion: 1, stage, growth, trunk: { height, thickness }, branches: [{ id, parentId (null = trunk), position, angle, length, thickness, bare }], leaves / flowers: [{ id, branchId, position, size }], fruits: [{ id, branchId, position, size }], decorations: [{ id, kind, branchId, position }], stats: { countedSessions, ignoredSessions, countedSeconds } }`. `position` is 0 (base) to 1000 (tip) along the parent; `angle` is whole degrees from the parent direction (negative left, positive right); lengths and sizes are abstract units (trunk at most 400 high). Parents come before children. Lists are bounded (40 branches + 80 twigs, 480 leaves, 120 flowers, 8 fruits, 100 decorations).

## Auth

Own JWT, no auth framework.

- **Access token:** JWT signed with `@nestjs/jwt` (HS256, secret `JWT_ACCESS_SECRET`, at least 32 characters), lifetime 15 minutes, claims only `sub` (user id), `iss` (`libro-api`), `aud` (`libro-app`), `iat` and `exp` - no email or other personal data. Verification accepts only HS256 and checks signature, `iss`, `aud`, `exp` / `nbf`, that `sub` is a UUID, that integer `iat` and `exp` are present, `iat` is not in the future and `exp - iat` is at most 15 minutes. Production refuses to start with a blank secret or a known non-secret value (`src/config/non-secret-values.ts`: the `.env.example` and test values). Sent as `Authorization: Bearer <token>`.
- **Refresh token:** opaque random value (32 bytes), stored only as a SHA-256 hash in the `auth` schema. A token family (one sign-in) expires 30 days after sign-in, an absolute limit: rotation carries the family expiry forward and never extends it.
- **Rotation:** every refresh revokes the presented token and issues a new one in the same family, atomically - one conditional update consumes the token only while it is active, and a replacement is issued only when exactly one row was consumed. Presenting an already revoked token revokes the whole family. Logout revokes the current token.
- **Passwords:** argon2id (`@node-rs/argon2`, m=19456 KiB, t=2, p=1) behind `PASSWORD_HASHER`. 10 to 128 characters (Unicode code points, after NFKC normalisation), no other composition rules. Never logged, never returned. Emails are stored trimmed and lower case (unique `users_email_key`). An account created by a provider sign-in has no password (`password_hash` is `NULL`); an email / password login for it answers `401 invalid_credentials` after verifying against the dummy hash, exactly like a wrong password.
- **Protected by default:** a global auth guard; open endpoints opt out with `@Public()` (`/health`, register, login, refresh, logout, Google nonce and sign-in). The current user comes from a `@CurrentUser()` decorator (`AuthenticatedUser`, `{ id }`), never from the request body. Guard, decorators and the `ACCESS_TOKEN_VERIFIER` interface are platform code in `src/http/authentication/`; the auth module provides the verifier, wired in `AppModule` (`AuthenticationModule.forRoot({ verifierFrom: [AuthModule] })`): `ExistingAccountAccessTokenVerifier` checks the JWT (`JwtAccessTokens` behind `SIGNED_ACCESS_TOKEN_VERIFIER`) and then that the user still exists (one primary-key lookup on `auth.users` per authenticated request, `EXISTS` on `users_pkey`; the price for refusing tokens of deleted accounts at once), so a token of a deleted user answers `401 invalid_access_token`. The guard runs after the app version guard, so an outdated app gets `426` before `401`.
- **Errors:** no or malformed `Authorization` header -> `401 authentication_required` (`WWW-Authenticate: Bearer`); invalid, expired or foreign token -> `401 invalid_access_token` (`WWW-Authenticate: Bearer error="invalid_token"`); wrong email or password -> `401 invalid_credentials` (same body for both); taken email -> `409 email_already_registered`; unknown, used, revoked or expired refresh token -> `401 invalid_refresh_token` (one body for every case); a Google token of a Google account not linked to the account being deleted -> `401 identity_not_linked`; a refresh token that is not 43 base64url characters -> `400 validation_failed`; rate limit -> `429 too_many_requests` with `Retry-After`.
- **Endpoints:** `POST /v1/auth/register` (`201`), `POST /v1/auth/login` (`200`) and `POST /v1/auth/refresh` (`200`, `{ refreshToken }`) answer `{ user: { id, email }, accessToken, tokenType: 'Bearer', expiresIn, refreshToken, refreshTokenExpiresIn }` (`refreshTokenExpiresIn` = seconds until the family expires); `POST /v1/auth/logout` (`{ refreshToken }`, `204` whether or not the token was known) revokes the family; `GET /v1/me` answers `{ id, email }`; `POST /v1/me/deletion` (`204`) deletes the account (see below). Refresh and logout are `@Public()` and rate limited like login, so an expired access token never blocks them.
- **Storage:** `auth.sessions` is the token family (`user_id` -> `users` `ON DELETE CASCADE`, absolute `expires_at`, `revoked_at`); `auth.refresh_tokens` holds the SHA-256 hex of each token (`refresh_tokens_token_hash_key`, `session_id` -> `sessions` `ON DELETE CASCADE`, `revoked_at` when used). Rotation, reuse detection and logout are SQL in `TypeOrmSessionRepository` behind `SESSION_REPOSITORY`; each runs in one transaction that first locks the session row (`FOR UPDATE OF session`, lock order session then token) and checks expiry against `clock_timestamp()` after the lock, so a concurrent logout, reuse revocation or expiry is never missed; `SessionService` is the one place that starts, refreshes and ends sessions and logs a detected reuse with the session id only.
- **Strict reuse rule:** two concurrent refreshes with the same token give one `200`; the other one finds the token used and revokes the family, so the winner's new tokens stop refreshing too and the app signs in again. This is deliberate: a token presented twice is treated as stolen.
- **Access tokens stay stateless for logout:** logout and family revocation do not reach access tokens already issued; they stay valid until their 15 minute expiry. Account deletion does reach them, through the user check of the verifier.
- **Follow-up:** no cleanup job removes expired or revoked sessions and used refresh tokens yet; add a periodic delete (e.g. sessions past `expires_at` or revoked for some days) before the tables grow.
- **Rate limit:** `@nestjs/throttler` on register, login, refresh, logout, Google nonce, Google sign-in and account deletion: `AUTH_RATE_LIMIT_MAX` requests (default 10) per client IP and route within `AUTH_RATE_LIMIT_WINDOW_SECONDS` (default 60). Storage is in memory, fine for one instance; more instances need a shared store (Redis, later). Behind a proxy, set `TRUST_PROXY` (exact hop count, or a list of trusted IPs / CIDR ranges / `loopback`, `linklocal`, `uniquelocal`; never `true`) so the client IP comes from `X-Forwarded-For`; unset trusts no proxy and forwarded headers are ignored. Login errors do not reveal whether the email exists: an unknown email is verified against a dummy argon2 hash, so both failures take comparable time.
- **Events:** the auth module publishes `UserRegistered` v1 (`{ userId }`) after the user is committed and `UserDeleted` v1 (`{ userId }`) after the deletion is committed; other modules (e.g. `profiles`) react to them and never read auth tables.
- **Account deletion (LIB-23):** `POST /v1/me/deletion` (authenticated, rate limited like login, `204`) deletes the account at once, no grace period. The body is exactly one of `{ password }` or `{ provider: 'google', idToken }` (two `z.strictObject` options of a union, deliberately: an ambiguous body with both, or with other fields, answers `400 validation_failed`). The password is checked like login (`PasswordCheckService`; an account without a password is verified against the dummy hash and answers `401 invalid_credentials`, like a wrong password). A Google confirmation is a fresh Google sign-in: a nonce from `POST /v1/auth/google/nonce`, the ID token verified and its nonce consumed exactly like sign-in (`IdentityTokenService.verifyOnce`), then its `(provider, sub)` must be an identity of this same user; a Google account linked to another user or to nobody answers `401 identity_not_linked` (one body for both, so it does not tell whether the Google account has another Libro account). Token and provider errors are those of Google sign-in. An account with both a password and Google may use either. On success one statement (`TypeOrmUserRepository.delete`) deletes the `auth.users` row (sessions, refresh tokens and identities cascade; sign-in nonces are not personal and expire) and inserts a tombstone into `auth.deleted_accounts` (`user_id` uuid primary key, `deleted_at`, `deleted_accounts_deleted_at_idx`; only the opaque id, no personal data); after the commit `UserDeleted` v1 is published and replayed after 2 and 10 minutes (see [Account deletion](#account-deletion)). The email is free again: registering it creates a new user with a new id.
- **Google sign-in (LIB-22):** the app signs in with native Google Sign-In (the SDK handles OAuth / PKCE on the device) and sends the Google ID token; the backend verifies it and issues our own tokens. No redirect / callback flow, no client secret; Google access tokens are never accepted or stored. Configured by `GOOGLE_CLIENT_IDS` (comma-separated OAuth client IDs: iOS, Android, web; trimmed, blanks dropped); empty turns Google sign-in off and both endpoints answer `503 identity_provider_not_configured` while the app still starts.
  - **Endpoints** (`@Public()`, rate limited like login): `POST /v1/auth/google/nonce` (`201 { nonce, expiresIn }`) issues a single-use nonce for one sign-in; `POST /v1/auth/google` (`{ idToken }`, a compact JWS of at most 4096 characters, `200`) answers the same session shape as login.
  - **Nonce:** 32 random bytes base64url, stored only as SHA-256 hex in `auth.sign_in_nonces` (`nonce_hash` primary key, `provider`, `expires_at`, `created_at`; `sign_in_nonces_expires_at_idx`), valid 10 minutes from the database clock (`clock_timestamp()`). Issuing also deletes at most 100 expired rows, so the anonymous endpoint cannot grow the table forever. Sign-in verifies the token first, then consumes the nonce of its `nonce` claim with one conditional `DELETE ... RETURNING` (unexpired, same provider), so of two concurrent requests with the same token exactly one succeeds. A rejected token leaves its nonce usable.
  - **Token validation** (in `identity-providers`, see below): OpenID Connect Core 1.0 section 3.1.3.7, RFC 8725 and RFC 9700 - only `RS256`, key chosen by `kid` from the Google JWKS; `iss` exactly `accounts.google.com` or `https://accounts.google.com`; every `aud` value must be one of our client IDs; `azp`, when present, must be one of them and is required when `aud` has several values; `exp`, `iat` and `nonce` required, `iat` not in the future and `exp` / `nbf` checked with 60 seconds clock tolerance; `sub` a non-empty string.
  - **Account linking:** the identity is matched by `(provider, sub)`, never by email. A known identity signs its user in and never changes the stored email. Otherwise the provider must mark the email verified (`email_verified === true`, else `403 identity_email_not_verified`); the email is normalised like registration. If no user has that email, a new user without password is created with the identity and `UserRegistered` v1 is published after commit. An existing user with that email gets the identity linked (a password keeps working) only when the provider is authoritative for the email (`emailAuthoritative`, decided per provider in `identity-providers`; for Google, following Google's account-linking guidance: verified and either a `gmail.com` address or a Workspace account whose `hd` claim equals the email domain, case-insensitively). For any other address `email_verified` only means Google verified it at some point, so it never takes over an existing account: `409 email_account_exists` (sign in with the password), no identity is stored and no second user is created; the decision is made inside the linking transaction. An authoritative link to a user that already has a Google identity with another `sub` answers `409 identity_conflict` (never relinked silently: a Google email can be reassigned to another person). The database part is one transaction in `TypeOrmIdentityRepository` behind `IDENTITY_REPOSITORY`: a transaction-scoped advisory lock on `(provider, sub)`, a re-read of the identity, `INSERT ... ON CONFLICT DO NOTHING` for the user and the identity; so concurrent first sign-ins with the same `sub` create one user and all answer `200`, and concurrent first sign-ins of two Google accounts with the same email give one `200` and one `409 identity_conflict`. If the user row of the email disappears between the insert and the locked lookup, the insert is retried up to 3 times in the same transaction, then the answer is `409 identity_conflict`, never a `500`.
  - **Storage:** `auth.identities` (`provider`, `subject`, `user_id` -> `users` `ON DELETE CASCADE`, `created_at`; unique `identities_provider_subject_key` and `identities_user_id_provider_key`, so one identity per provider and user). Reverting the migration keeps passwordless users: each gets an argon2id hash of a discarded random secret, so nobody knows its password.
  - **Errors:** any signature, claim or nonce failure -> `401 invalid_identity_token` (only token errors: bad signature or claims, malformed token, disallowed or unsupported algorithm, no or several matching keys; one body for every case; the reason is logged at debug level, never the token); unverified email -> `403 identity_email_not_verified`; an existing account with an email the provider is not authoritative for -> `409 email_account_exists`; email account linked to another Google account -> `409 identity_conflict`; not configured -> `503 identity_provider_not_configured`; the Google keys cannot be fetched (timeout, network error, error status, invalid JSON or key set) -> `503 identity_provider_unavailable` (the app may retry with the same token and nonce; the cause is logged at warn level); malformed body -> `400 validation_failed`; rate limit -> `429 too_many_requests`.
  - **Accepted MVP risk:** email registration does not verify the email yet, so account pre-hijacking is possible (someone registers a victim's email with a password before the victim's first Google sign-in links to it). It closes when email verification / password reset by email arrives; do not work around it before then.
- **Apple (LIB-24):** same flow as Google through `identity-providers` (see below).
- **On the device:** the app keeps tokens in `expo-secure-store`.

## Identity providers

Module `identity-providers`: only verifies provider ID tokens. No tables, no users; `auth` owns accounts and linking.

- **Public interface:** `IDENTITY_TOKEN_VERIFIER` (`IdentityTokenVerifier`): `isConfigured(provider)` and `verify(provider, idToken)`, which answers a `VerifiedIdentity` (`{ provider, subject, email, emailVerified, emailAuthoritative, nonce }`, plain data) or throws `InvalidIdentityTokenException` (`401 invalid_identity_token`), `IdentityProviderNotConfiguredException` (`503 identity_provider_not_configured`) or `IdentityProviderUnavailableException` (`503 identity_provider_unavailable`); all three are exported from `index.ts`.
- **Strategy:** one generic `OidcIdTokenVerifier` over `jose` (`jwtVerify` with an `RS256` allowlist, issuers, audiences, required claims, clock tolerance, plus checks of every `aud`, `azp` and `iat`), parameterised by an `OidcProviderConfig` (`provider`, `issuers`, `clientIds`, `signingKeys`, `isEmailAuthoritative`: the provider's rule whether its verified email proves current ownership, from `email`, `email_verified` and `hd`). `IdentityTokenVerifiers` selects the verifier by provider name; a provider without client IDs counts as not configured.
- **Signing keys:** behind an injection token per provider (`GOOGLE_SIGNING_KEYS`, a `jose` `JWTVerifyGetKey`); production uses `createRemoteJWKSet` on `https://www.googleapis.com/oauth2/v3/certs`, which caches the keys and refetches on an unknown `kid`. Integration tests override the token with a local JWKS of a key pair generated in the test, so tests never call Google. Only token errors map to `401 invalid_identity_token` (an allowlist of `jose` errors); every other failure of the key source (timeout, network error, error status, invalid JSON, invalid key set or key) throws `IdentityProviderUnavailableException` (`503 identity_provider_unavailable`, exported from `index.ts`) and logs the cause at warn level without the token.
- **Adding a provider (e.g. Apple):** add the name to `IDENTITY_PROVIDERS`, a `providers/<name>.provider.ts` with its issuers, client IDs from env, its email authority rule and a `<NAME>_SIGNING_KEYS` token, list it in `oidcProviderConfigs`, extend the `provider` CHECK constraints of `auth.identities` and `auth.sign_in_nonces` in a migration, and add the two endpoints (`/v1/auth/<name>/nonce`, `/v1/auth/<name>`) next to the Google ones; `SignInNonceService` and `IdentitySignInService` already take the provider. Provider quirks (e.g. Apple hashing the nonce) belong in the provider config, not in `auth`.

## Account deletion

Immediate, after confirming with the password or a fresh Google sign-in (see [Auth](#auth)). Shared things are deleted, never anonymised.

- **Event:** auth deletes the user, writes the tombstone, then publishes `UserDeleted` v1 (`{ userId }`, from `modules/auth/index.ts`).
- **Handlers:** every module that stores user data deletes it in its own repository, idempotently (a re-run deletes nothing more and fails nothing): `reading-sessions` the readings and sessions of the user (checkpoints, marked parts and every group participation of those sessions, as host or participant, cascade; the other members' sessions go on alone) and the user's `reading.sharing_settings` row; `tree` the `tree.finished_trees` rows; `media` all media rows of the user in one transaction (under the per-owner advisory lock) that also records their files in `media.pending_file_deletions`, then the files (see Media, Consistency); `profiles` the profile (top books and follows in both directions cascade); `feed` the posts of the user (their likes, reactions, photo links and post activities cascade), the user's reading activities and the user's likes and reactions on posts of others, in one transaction under the per-author advisory lock of the post limit; `reviews` all `reviews.reviews` rows of the user; `encouragements` every insight and congratulation the user wrote or received (author or reader), in one transaction. `books` holds no user data.
- **Deadlocks:** erasing two users concurrently can deadlock when deleting one user's rows cascades into rows of the other one (follows in both directions, likes and reactions on each other's posts, group participations of two users reading in each other's groups, insights and congratulations two users wrote on each other's readings). Erasure repositories therefore run their whole transaction through `retryOnDeadlock(DEADLOCK_RETRY_ATTEMPTS, work)` (`src/database/deadlock.ts`, `isDeadlock` checks SQLSTATE `40P01`): up to 3 attempts, a fresh transaction each time, every other error unchanged. `feed`, `profiles`, `reading-sessions` and `encouragements` use it; a new erasure that cascades across users uses it too.
- **Stale tokens:** the access token verifier refuses tokens of a user that no longer exists, so a token issued before the deletion cannot recreate a profile, a session, a follow or a photo. There is no cross-module lock: a request that passed the guard just before the deletion committed (a slow upload, a session start, a lazily provisioned profile, a follow) can still write after the handlers ran. Such a write is erased by the delayed replay or, at the latest, by the next purge run.
- **Delayed replay:** after a successful deletion `DeletionReplayService` schedules `UserDeleted` v1 again for that user after 2 and after 10 minutes (`DELETION_REPLAY_DELAYS_MS`) through `TASK_SCHEDULER` (`TaskScheduler`; `TimerTaskScheduler` uses `setTimeout`, unref'd so it never keeps the process alive, clears every timer on application shutdown and logs a failing task). In process only: a restart loses the replays, the purge command is the durable backstop. Tests replace `TASK_SCHEDULER` with a manual scheduler and trigger the replays without waiting.
- **Purge command (lost events, failed handlers, failed file deletions):** `pnpm accounts:purge-deleted` (root alias of `pnpm --filter @libro/api run accounts:purge-deleted`; `src/cli/purge-deleted-accounts.ts`, a Nest application context running `purgeDeletedAccounts` from `src/cli/deleted-accounts-purge.ts`) runs three steps in this order: publish `UserDeleted` v1 again for every tombstone (`DELETED_ACCOUNTS_PURGE.replayAll()`, pages of 100 in `user_id` order), retry every pending media file deletion (`MEDIA_FILE_DELETIONS.retryPending()`), and only then forget tombstones older than 30 days (`forgetExpired()`, `DELETED_ACCOUNT_RETENTION_DAYS`), so an expiring tombstone gets its last replay in the same run. It logs the counts and exits with code 1 when a pending media file deletion still failed in that run, so a cron alert fires. Handler failures are logged as usual (`DomainEvents`, error level); an operator watches the logs. Safe to run any time and repeatedly. **Production must run it regularly, e.g. a daily cron job**: with a daily run every tombstone is replayed about 30 times before it expires, then nothing of the account remains.
- **No trace test:** `apps/api/test/modules/account-deletion/no-trace-after-deletion.e2e.test.ts` arranges a full account (profile, avatar, top books, follows both ways, a post with a photo and with likes and reactions both ways, the feed activities of the post and the readings, photos with files, finished and open readings with sessions, checkpoints and marked parts, the reading privacy setting, a participant (a factory session) in the group of the open session, a finished tree, a review of the finished reading with a photo, an insight and a congratulation given to the other arranged account and received from it, a Google identity, sign-ins) and requires, table by table, that every table in every non-system schema holds at least one row referencing the user or one of their ids, except the tables in `TABLES_WITHOUT_USER_DATA` (each with its reason: the `books` catalogue tables, `auth.sign_in_nonces`, the tombstone table, the transient `media.pending_file_deletions`, `public.migrations`); a new table without arranged data and without an exclusion fails the test with its name. It then deletes the account and scans every row of every table (the whole row as lower-case text, against the lower-case ids with and without hyphens and the email; only `auth.deleted_accounts` is skipped) for the user id, email and the ids of the user's sign-ins, photos, readings and sessions, plus the media storage directory for the photo files.
- **New modules:** a module that stores user data adds a `UserDeleted` handler and extends the arranged account in the test fixture (see Module conventions); like `feed` and `encouragements`, a module deletes the user's rows on other users' content too.

## Reading sessions

Module `reading-sessions`, Postgres schema `reading`.

- **Model:** a reading is one read-through of a book (work) by a user (`reading.readings`: `user_id`, `work_id`, `started_at`, `finished_at`); at most one unfinished reading per user and work (`readings_unfinished_user_id_work_id_key`). A session belongs to a reading (`reading.sessions`, `status` `active` | `paused` | `ended`, optional `place`); checkpoints (`reading.checkpoints`, `page`) and marked parts (`reading.marked_parts`, `kind` `good` | `slow` | `skipped`, `from_page` to `to_page`) belong to a session. Sessions, checkpoints and marked parts cascade on delete. `user_id` and `work_id` are ids of other modules without FKs; the work is checked through `BOOK_CATALOGUE.workExists`.
- **One open session per user:** a partial unique index (`sessions_open_user_id_key`, `status <> 'ended'`), so a second or concurrent start answers `409`. Starting attaches the session to the unfinished reading of the book or creates one, in one transaction (upsert of the reading row, then the session insert; lock order reading then session).
- **Server time only:** every timestamp comes from the database clock in the repository SQL (`clock_timestamp()`; a start uses the transaction time `now()` so a new reading and its first session share it); client timestamps are not accepted. Active time is `active_seconds` (finished active stretches) plus the running stretch since `active_since` (set only while `active`), so pauses never count. `activeSeconds` in responses is whole seconds.
- **Transitions:** `pause` (active -> paused), `resume` (paused -> active), `end` (active or paused -> ended); of two concurrent requests only one succeeds. Checkpoints only while `active`, marked parts while `active` or `paused`.
- **Lock, then clock:** every session write is one transaction that first locks the owned session row in an allowed status (`FOR UPDATE`, so transitions, checkpoints and marked parts of one session are serialised and the per-session caps cannot be exceeded by concurrent inserts; no row -> 404 or 409) and only then writes with `clock_timestamp()`, so time is sampled after any lock wait and an end never gets an `ended_at` before a checkpoint that committed while it waited.
- **Finishing:** only when the user explicitly finishes the book. Finish locks the reading (`FOR UPDATE`), refuses while a session of it is open, then sets `finished_at`. The next session of the same book starts a new reading (re-read).
- **Input:** pages are integers 1 to 100000 (editions have no page count yet); `fromPage` must not exceed `toPage`; place is trimmed, at most 100 characters, blank becomes `null`. A session holds at most 500 checkpoints and 100 marked parts (counted by the insert itself under the session lock), so a reading's history stays bounded per session. No anti-cheat rules here, only nonsense input is rejected.
- **Endpoints** (all authenticated; another user's session or reading answers `404` exactly like an unknown id): `POST /v1/reading-sessions` (`{ workId, place? }`, `201`), `GET /v1/reading-sessions/current`, `GET /v1/reading-sessions/:sessionId`, `POST /v1/reading-sessions/:sessionId/pause`, `/resume`, `/end` (`200`) answer `{ id, readingId, workId, place, status, startedAt, endedAt, activeSeconds, checkpoints: [{ id, page, recordedAt }], markedParts: [{ id, kind, fromPage, toPage, createdAt }], groupHostSessionId }` (`groupHostSessionId`: see Reading groups); `POST /v1/reading-sessions/:sessionId/checkpoints` (`{ page }`, `201`, the checkpoint); `POST /v1/reading-sessions/:sessionId/marked-parts` (`{ kind, fromPage, toPage }`, `201`, the marked part); `POST /v1/readings/:readingId/finish` (`200`, `{ id, workId, startedAt, finishedAt }`).
- **Errors:** unknown book -> `404 book_not_found`; another open session (also when joining) -> `409 reading_session_already_open`; unknown or foreign session, or no open one for `current` -> `404 reading_session_not_found`; transition not allowed from the current status -> `409 invalid_session_transition`; checkpoint outside an active session -> `409 reading_session_not_active`; marked part in an ended session -> `409 reading_session_ended`; unknown or foreign reading -> `404 reading_not_found`; finish while a session of the reading is open -> `409 reading_session_open`; finish twice -> `409 reading_already_finished`; a checkpoint or marked part over the per-session cap -> `409 reading_session_limit_reached`; invalid input -> `400 validation_failed`.
- **Events:** `ReadingStarted` v1 (`{ readingId, userId, workId }`), `SessionEnded` v1 (`{ sessionId, readingId, userId, workId }`) and `BookFinished` v1 (`{ readingId, userId, workId }`), published after commit. `ReadingStarted` is published only when starting a session or joining a group created a new reading row, never when the session attached to an unfinished reading of the book (the upsert reports it with `xmax = 0`); a re-read is a new reading, so it publishes again.
- **Public interface:** `READING_HISTORY` (`ReadingHistory`) for other modules: `findReading(userId, readingId)` (`undefined` for an unknown or foreign reading) and `listReadings(userId, { finished, limit, offset })` (finished: latest `finished_at` first; unfinished: latest `started_at` first) answer readings with only their ended sessions (`activeSeconds` in whole seconds, `checkpoints: [{ page }]`, `markedParts: [{ kind, fromPage, toPage }]`, `groupHostSessionIds`: the host session of the group the session joined, if any, then the session itself when it ever had a participant; history, so leaving or removal does not drop it), in two queries whatever the page size. `findReadingSummary(readingId, ownerIds)` answers `{ readingId, userId, workId, finishedAt }` of the reading when its owner is one of `ownerIds` (one query, `undefined` otherwise); it is meant for modules that act on someone else's reading (`encouragements`): the caller decides who may act and passes that audience, so an unknown reading and a reading outside it look the same. `ReadingNotFoundException` and the `ReadingSummary` type are exported too. `READING_ACTIVITY_SHARING` (`ReadingActivitySharing`): `sharingWithFollowers(userIds)` answers the set of the given users who share their reading activity with followers (`reading_activity = 'followers'` or no settings row), in one query; ids are deduplicated, at most 2001 distinct ids per call (`MAX_READING_ACTIVITY_SHARING_CHECKS_PER_CALL`, the viewer plus the 2000 follows cap; more throws a `RangeError`), no ids means no query.
- **Follow-up:** anti-cheat flags for suspicious sessions (impossible pace, very short sessions, ...) belong to the tree module (LIB-29), computed from the stored data. Offline sessions with client timestamps are not supported.

### Who is reading now and reading groups (LIB-28)

Polling over the normal API for now (a realtime WebSocket gateway later). Everyone keeps their own session and timer; a group only links sessions.

- **Privacy:** `reading.sharing_settings` (`user_id` uuid primary key without FK, `live_sessions` text CHECK `followers` | `nobody` (`sharing_settings_live_sessions_check`), `reading_activity` text NOT NULL DEFAULT `followers` CHECK `followers` | `nobody` (`sharing_settings_reading_activity_check`; who sees the started and finished books in the feed, see [Feed](#feed)), `updated_at`); a missing row means `followers` for both. `GET /v1/me/reading-privacy` answers `{ liveSessions, readingActivity }`; `PUT /v1/me/reading-privacy` (`{ liveSessions?, readingActivity? }`, at least one, else `400 validation_failed` with `errors[].path` `''`; `200`) changes only the settings sent and keeps the others (one upsert with `coalesce`, so concurrent changes of the two settings never undo each other; a new row gets the defaults for the missing one), so an old app sending only `{ liveSessions }` keeps working. A change applies at once, also to a session already open and to reading activity already in the feed.
- **Visibility (one rule, `persistence/session-groups.sql.ts`):** viewer V sees session S of user U when V = U (any status), or S is open (active or paused) and either U shares with `followers` and V follows U, or V and S read in the same current group (host or current participant; group members always see each other, whatever they share). The follows come from `SOCIAL_GRAPH.followeeIdsOf(V)` (at most 2000 ids) and go into the SQL as a parameter; the rule is one SQL predicate (`audienceOf` / `visibleTo` with the `viewer_group` CTE) used by the live list, the group view, join and participant counts, so it is never re-implemented in code. A session V may not see answers `404 reading_session_not_found`, exactly like an unknown id.
- **Groups:** `reading.session_participants` (`participant_session_id` uuid primary key and FK -> `sessions` `ON DELETE CASCADE`, `host_session_id` FK -> `sessions` `ON DELETE CASCADE` (`session_participants_host_session_id_idx`), `joined_at`, `left_at`, `removed_at`; CHECKs `session_participants_not_self_check`, `left_at` / `removed_at` not before `joined_at`). Rows are kept after leaving or removal (history for the tree). A participation is current while it has no `left_at` and no `removed_at` and both sessions are open (`currentParticipantsFrom`, the only definition, used for the cap, counts, the group view and the group root); a session's current group root is the host of its current participation, or the session itself while it is open and has a current participant. So ending the host session ends the group: its participants keep reading alone (`groupHostSessionId` becomes `null`), and a participant who ends, leaves or is removed is no longer in it. `groupHostSessionId` in session responses is that current root (`null` when reading alone).
- **Join:** `POST /v1/reading-sessions/:sessionId/join` (`{ place? }`, body optional, `201`) starts the joiner's own session of the same book (in their unfinished reading of it, created if needed) as a participant of the group: joining a participant joins its host's group (the root). Visibility is checked on the session joined, not on the host, so a host shown only through a participant is joinable through that participant. A participant whose host ended is a solo session again, so joining it makes it the host of a new group. Checks in this order, so nothing about a session the joiner may not see leaks: may not see under the visibility rule (another user's ended session included, so an ended session answers exactly like an unknown id) -> `404 reading_session_not_found`; own session -> `409 cannot_join_own_session`; the joiner has an open session -> `409 reading_session_already_open` (the unique index backs it); the group's host session ended after this authorisation (seen under its lock) -> `409 reading_session_ended`; removed from that group before -> `403 removed_from_group` (a host decision, not a state conflict); 20 current participants (`MAX_GROUP_PARTICIPANTS`, host not counted) -> `409 group_full`.
- **Leave and remove:** `POST /v1/reading-sessions/:sessionId/leave` (`200`, the own session, which goes on alone) sets `left_at`; a session that is no current participant (a host, a solo session, after the host ended) -> `409 not_in_group`. A reader who left may join again with a new session. `DELETE /v1/reading-sessions/:hostSessionId/participants/:participantSessionId` (`204`, host only; anyone else's or an unknown host session -> `404 reading_session_not_found`, an ended host session -> `409 reading_session_ended`, a session that never joined it -> `404 group_participant_not_found`) sets `removed_at` on any participation of that session in the group (also one that already left), idempotently (`204` again); the removed reader's session goes on alone and that reader can never join that group again.
- **Locks:** lock order is host session, then participant session (`FOR UPDATE`), always: participants are created after their host, so the order follows creation and cannot form a cycle. Join is one transaction: visibility and the open-session check, then the group root is resolved and its session locked; if the target stopped being a current participant meanwhile, the target itself is locked as the new root; then the removal check, the count of current participants and one statement that samples `clock_timestamp()` once (after the lock) for the upserted reading, the new session (`started_at`, `active_since`) and `joined_at`. So of two concurrent joins at the cap exactly one succeeds. Leave locks the host, then the own session, then sets `left_at` with `clock_timestamp()`; remove locks the owned host session, then checks under that lock that the given session is or was a participant of this host (rows of a host are only written under its lock) and answers `404 group_participant_not_found` for any other session without locking it, and only then locks the participant session and sets `removed_at`; so crossed removals (`A/participants/B` and `B/participants/A`) never lock in reverse order (B can never also host A). Transitions still lock only their own session, so a host ending never waits for its participants.
- **Live list:** `GET /v1/reading-sessions/live?limit=&offset=` (`limit` 1 to 50, default 20; `offset` 0 to 1000; `nextOffset` as in book search) answers `{ items: [{ sessionId, readingId, host: profile summary, book: { id, title, authors } | null, place, status, startedAt, progressPage, participantCount, joinedByMe }], nextOffset }` (`readingId` so a follower can add an insight, see [Encouragements](#encouragements)): the open sessions of the people the viewer follows that the viewer may see, most recently started first (the own session is never in it). `progressPage` is the page of the latest checkpoint (`null` before the first), `participantCount` the current participants of the session's group the viewer may see (host not counted; a member of the group sees every one, an outsider only those visible to them, so hidden participants are never revealed; the 20-participant cap counts all of them), `joinedByMe` whether the viewer reads in the same group. An item whose host has no profile is left out. Bounded: one `followeeIdsOf`, one query for the page (index `sessions_open_user_id_key` on `user_id = ANY (...)`), one `PROFILE_DIRECTORY.findSummaries` and one `BOOK_CATALOGUE.findWorkSummaries` call (at most 50 ids each, under their 100-id limits), whatever the page size; no followees means no query.
- **Group view:** `GET /v1/reading-sessions/:sessionId/group` (a session the viewer may see) answers `{ book, host: member | null, participants: [member] }`, member `{ sessionId, readingId, reader: profile summary, place, status, startedAt, progressPage, joinedAt (null for the host) }`: the group of the session's current root (a solo session, also an ended host session viewed by its owner, is a host without participants), current participants (both sessions open) in the order they joined; each member only when the viewer may see that member's session (so `host` is `null` for an outsider who may see only a participant). Two queries plus one profile and one catalogue call.
- **Follow-up:** realtime presence and push (`realtime` module, Redis); moderation beyond removal (blocking); a `SessionJoined` event once a consumer needs it.

## Tree

Module `tree`, Postgres schema `tree`. The tree rule applies: nothing about the shape is stored.

- **Storage:** only `tree.finished_trees` (`reading_id` primary key, `user_id`, `tree_engine_version` smallint `> 0`, `created_at`; `finished_trees_user_id_idx`), no FKs to other modules. Every request computes the tree with `computeTree`.
- **Input:** read through `READING_HISTORY` (public interface of `reading-sessions`), never from reading tables: `seed` = reading id, `finished` = `finishedAt` set, the ended sessions in order (`started_at`, `id`) with their checkpoints and marked parts in stored order, and the decorations: first one `group_reading` decoration per distinct group of the reading's ended sessions (`{ id: 'group:' + hostSessionId, kind: 'group_reading' }`, in session order, from `groupHostSessionIds`), then the insights and congratulations of followers, oldest first (`{ id: 'insight:' + insightId, kind: 'insight' }`, `{ id: 'congratulation:' + authorId, kind: 'congratulation' }`, at most 100, from `READING_ENCOURAGEMENTS.decorationsFor`, public interface of `encouragements`, never its tables). The engine keeps the first 100 and places each one from the seed and its own id, so the order only decides which ones are kept at the limit: new encouragements are appended, a new group (only while the reading is in progress) is inserted before them. Decorations never change the shape, so a finished tree keeps its shape when a decoration appears or disappears (e.g. a congratulation arrives, an insight is deleted, or the other member's account is deleted and its rows go away). Open sessions never count; short or checkpoint-less sessions are passed on and the engine ignores them.
- **Versions:** a reading in progress grows with `LATEST_TREE_ENGINE_VERSION`. A `BookFinished` v1 handler records the reading with the latest version (`ON CONFLICT DO NOTHING`); a finished reading is always computed with its stored version, so it never changes shape. Events can be lost, so a finished reading without a row gets one with the latest version on its first read (same idempotent insert). A stored version the engine does not know is logged and answers `500 tree_engine_version_unavailable`; never fall back to another version.
- **Queries:** one reading or a whole page costs the same bounded number of queries: readings, their ended sessions with checkpoints and marked parts (`json_agg`), stored versions and one `decorationsFor` call for the whole page (run in parallel with the versions), plus an insert and a re-read when some finished readings have no row yet.
- **Endpoints** (authenticated, owner only; another user's reading answers `404 reading_not_found` exactly like an unknown id): `GET /v1/readings/:readingId/tree` answers `{ readingId, workId, finished, finishedAt, tree }` (`tree` is the engine output with its `treeEngineVersion`, schema `TreeV1`); `GET /v1/me/forest` (finished readings, latest `finishedAt` first) and `GET /v1/me/growing-trees` (unfinished readings, latest `startedAt` first) answer `{ items: [same shape], nextOffset }` with `limit` 1 to 20 (default 20; lower than book search because sessions per reading are not capped, so one tree can be large) and `offset` 0 to 1000 (default 0); `nextOffset` works as in book search.
- **Visibility:** trees and the forest are visible only to their owner for now.
- **Follow-up:** sharing trees with followers; caching computed trees only if computing ever gets expensive.

## Reviews

Module `reviews`, Postgres schema `reviews`. After finishing a book the reader rates it and may write a few words. A review belongs to one reading (read-through), so a re-read can get its own review.

- **Writing:** `PUT /v1/readings/:readingId/review` (`{ rating, text?, photoId? }`) creates or replaces the whole review and always answers `200` with it (one rule for create and replace; a left out text or photo removes the current one). `rating` is a whole number of stars, 1 to 5. `text` is NFC-normalised and trimmed, at most 1000 characters (Unicode code points); blank, `null` or left out stores `NULL`. CHECKs back both up (`reviews_rating_check`, `reviews_text_check`).
- **Photo of the finished book:** `photoId` must be a photo of the reader (`MEDIA_LIBRARY.findOwned`), else `404 media_not_found` and nothing changes; `null` or left out stores no photo. The reading is checked first, so a foreign reading answers `404 reading_not_found` whatever the photo. The media id is kept without FK (`photo_media_id`). Answers sign the URLs with `MEDIA_LIBRARY.findMany`, only for the photos readers attached to reviews the viewer may see; a deleted photo answers `photo: null`, never an error.
- **Only finished, only own:** the reading is checked through `READING_HISTORY.findReading(userId, readingId)` (public interface of `reading-sessions`), never through reading tables: unknown or another user's reading -> `404 reading_not_found`, a reading in progress -> `409 reading_not_finished`. `work_id` and `finished_at` are copied from the reading when the review is written (finishing is final, so they never go stale), which keeps lists to one query without a batch lookup in `reading-sessions`.
- **Timestamps:** `created_at` and `updated_at` come from the database clock (`clock_timestamp()`, sampled once per insert); replacing keeps `created_at`, so a review keeps its place in the lists.
- **Concurrency:** one transaction tries `INSERT ... ON CONFLICT (reading_id) DO NOTHING RETURNING`, then updates the row; of concurrent first writes exactly one creates (and publishes `ReviewPublished`), the others replace, and all answer `200`.
- **Visibility:** a review is visible to its reader and to the readers following them (`SOCIAL_GRAPH`), nobody else. `GET /v1/readings/:readingId/review` answers `404 review_not_found` for anyone else exactly like a missing review, so existence is never revealed, not even by timing: the viewer's audience (`followeeIdsOf` plus the viewer) is resolved first, whatever the review, and one lookup constrained to it (`reading_id = $1 AND user_id = ANY($ids)`) finds the review or nothing, so a hidden and a missing review take the same queries. `DELETE` is owner only (`204`), one conditional delete (`reading_id` and `user_id`); no own review -> `404 review_not_found`.
- **Lists (keyset):** `GET /v1/profiles/:userId/reviews` (that user's reviews; the user and their followers only, anyone else and an unknown user get an empty page, which reveals no more than a `404` would) and `GET /v1/books/:workId/reviews` (the reviews of that work by the viewer and the readers they follow: `SOCIAL_GRAPH.followeeIdsOf`, at most 2000, plus the viewer, as `user_id = ANY($ids)`; an unknown work gets an empty page). Newest first by `(created_at, reading_id)` descending, paged with an opaque `cursor` exactly like the feed (`nextCursor` of the previous page, canonical base64url JSON `{ createdAt, readingId }` with microseconds; `null` on the last page); `limit` 1 to 50 (default 20); an invalid cursor -> `400 validation_failed` (`errors[].path` `cursor`). The cursor of one list is accepted by the other.
- **Queries:** a page costs the same bounded number of queries whatever its size: one `isFollowing` (profile list of someone else) or one `followeeIdsOf` (book list), one query for the rows, one `PROFILE_DIRECTORY.findSummaries` call (plus its media call when a reader has an avatar), one `BOOK_CATALOGUE.findWorkSummaries` call and one `MEDIA_LIBRARY.findMany` call when a review has a photo; a page has at most 50 distinct readers, works and photos, under the 100-id maxima.
- **Shape:** a review is `{ readingId, readerId, reader, book: { id, title, authors: [{ id, name }] } | null, rating, text, finishedAt, createdAt, updatedAt, photo }`; `reader` is a profile summary `{ userId, handle, displayName, avatar, official, followedByMe }` or `null` (a reader without a profile, next to the always present `readerId`, like the feed's `authorId`); `book` is `null` for a work no longer in the catalogue. `photo` is `{ mediaId, width, height, variants: { small, medium, large: { url, width, height } }, urlsExpireAt }` (the same shape as a post photo; `width` / `height` of the `large` variant) or `null` (no photo, or a deleted one); it was always `null` before LIB-33, so filling it is additive. Pages are `{ items, nextCursor }`. UUIDs in paths are accepted in any case and lower-cased.
- **Errors:** unknown or foreign reading on write -> `404 reading_not_found`; unfinished reading -> `409 reading_not_finished`; a photo that is not an own photo -> `404 media_not_found`; missing, foreign-and-not-followed or foreign on delete -> `404 review_not_found`; invalid input (rating, text length, ids that are not UUIDs, page limits, invalid cursor) -> `400 validation_failed`.
- **Data:** `reviews.reviews` (`reading_id` uuid primary key, `user_id`, `work_id` (both without FK), `rating` smallint, `text`, `photo_media_id` uuid nullable without FK (the media id), `finished_at`, `created_at`, `updated_at`; `reviews_user_id_created_at_reading_id_idx` for the profile list and account deletion, `reviews_work_id_user_id_created_at_reading_id_idx` for the book list, so the audience filter is an index condition and only the visible reviews of the work are read, then the top of the page is sorted; the profile list reads its index backwards for newest first).
- **Events:** `ReviewPublished` v1 (`{ readingId, userId, workId }`), published after commit when a review is first created (not on replace), for notifications later.
- **Public interface:** `READING_REVIEWS` (`ReadingReviews`): `findForReadings(readingIds)` answers a map of reading id -> `{ readingId, rating, text, photoMediaId }` for the readings that have a review, whoever wrote it (one query, `reading_id = ANY`; ids deduplicated, at most 100 distinct ids per call, `MAX_READING_REVIEWS_PER_CALL`, more throws a `RangeError`; no ids means no query). The caller makes the authorisation decision: `feed` asks only for readings whose `book_finished` activity the viewer may see, whose audience (the reader and followers) is the review audience. The photo id is signed by the caller through `MEDIA_LIBRARY.findMany`.
- **Account deletion:** a `UserDeleted` v1 handler (`EraseReviewsHandler`) deletes all reviews of the user (`DELETE ... WHERE user_id = $1`, idempotent); other readers' reviews of the same books stay.
- **Follow-up:** showing reviews in the feed on `ReviewPublished`; average ratings per book; extracting the keyset cursor shared with the feed into platform code.

## Encouragements

Module `encouragements`, Postgres schema `encouragements` (LIB-32). Followers water a reader's tree: an insight (a short thought) to a book the reader is reading and a congratulation on a finished book become `insight` and `congratulation` decorations of the tree (the tree rule applies: the tree is computed from these rows, nothing is drawn or stored).

- **Who:** only a reader who follows the reader (`SOCIAL_GRAPH`) encourages them, never on the own reading. The target is a reading id (from the live list or the group view for a reading in progress, from a review for a finished one). The reading is found through `READING_HISTORY.findReadingSummary(readingId, [author, ...followeeIdsOf(author)])`, never through reading tables: the author's audience is resolved first whatever the reading, so an unknown reading and a reading of someone the author does not follow take the same queries and answer the same `404 reading_not_found`; the own reading -> `409 cannot_encourage_own_reading` (`*_not_own_check` CHECKs back it up). `reader_id` is copied from the reading when a row is written (a reading never changes owner), for the reader's moderation and account deletion.
- **Insight:** `POST /v1/readings/:readingId/insights` (`{ text }`, `201`) only on a reading in progress (finished -> `409 reading_finished`). `text` NFC-normalised and trimmed, 1 to 300 characters (Unicode code points, `insights_text_check`). At most 3 insights per author and reading (`MAX_INSIGHTS_PER_AUTHOR_AND_READING`) -> `409 insight_limit_reached`: the check is the insert itself (`INSERT ... SELECT ... WHERE (count) < 3`) under the reading lock (see Order), so concurrent requests never pass the limit; a deleted insight no longer counts. Answers `{ id, readingId, decorationId, authorId, author, text, createdAt }`. Insights cannot be edited. `DELETE /v1/insights/:insightId` (`204`) by its author or by the reader of the reading (moderation of the own tree), one conditional delete; anyone else, an unknown or an already deleted insight -> `404 insight_not_found`.
- **Congratulation:** `PUT /v1/readings/:readingId/congratulation` (`204`) only on a finished reading (in progress -> `409 reading_not_finished`), once per author and reading (primary key `(reading_id, author_id)`, `INSERT ... ON CONFLICT DO NOTHING`), so repeated and concurrent requests all answer `204` and store one row. A re-read is a new reading and can be congratulated again. `DELETE /v1/readings/:readingId/congratulation` (`204` always, no reading check, so it reveals nothing) withdraws the own congratulation, also after unfollowing. `DELETE /v1/readings/:readingId/congratulations/:authorId` (`204`, idempotent) lets the reader remove a congratulation from the own reading; a reading that is not the caller's -> `404 reading_not_found`.
- **Order (append-only):** every insight and congratulation insert is one transaction that first takes a transaction-scoped advisory lock on the reading (`hashtextextended('encouragements/' || reading_id)`, the only lock it takes, shared by both tables) and only then samples `created_at` with `clock_timestamp()`. So writes on one reading commit in `created_at` order: a decoration that was shown can never be pushed out of the first 100 by a write that started earlier and committed later. Deletes take no lock (they only remove).
- **No cross-module lock:** an insight checked just before the reading is finished can be stored right after it; harmless, decorations never change the shape of the tree.
- **List:** `GET /v1/readings/:readingId/encouragements?cursor=&limit=` answers `{ items: [{ decorationId, kind, insightId, authorId, author, text, createdAt }], nextCursor }`: for the reader every insight and congratulation of the reading, for a follower of the reader only their own, anyone else (the audience rule above) `404 reading_not_found`. `kind` is `insight` | `congratulation`; `insightId` and `text` are `null` for a congratulation; `author` is a profile summary or `null` (no profile); `decorationId` is the id of the decoration on the tree, so the app can show who watered which part. Followers are not capped, so the list is paged, not answered whole: newest first by `(created_at, decorationId)` descending (`decorationId` compared `COLLATE "C"`), keyset pages like reviews (opaque canonical base64url JSON `{ createdAt, decorationId }` with microseconds, `null` on the last page; `limit` 1 to 50, default 20; an invalid cursor -> `400 validation_failed`, `errors[].path` `cursor`). A page costs the same queries whatever its size: one `followeeIdsOf`, one `findReadingSummary`, one query over both tables (each branch limited to the page on its `reading_id, created_at` index) and one `PROFILE_DIRECTORY.findSummaries` call (at most 50 authors).
- **Public interface:** `READING_ENCOURAGEMENTS` (`ReadingEncouragements`): `decorationsFor(readingIds)` answers a map of reading id -> decorations (readings without any are left out): at most 100 per reading (`MAX_DECORATIONS_PER_READING`, the engine's limit), the oldest first by `(created_at, decoration id)`, `{ id: 'insight:' + insightId, kind: 'insight' }` and `{ id: 'congratulation:' + authorId, kind: 'congratulation' }`. One query for the whole batch (a lateral per reading that reads at most 100 rows of each table through `insights_reading_id_created_at_id_idx` and `congratulations_reading_id_created_at_author_id_idx`); ids deduplicated, at most 100 distinct readings per call (`MAX_DECORATED_READINGS_PER_CALL`, more throws a `RangeError`: a programmer error, chunk the ids). Oldest first and appended in commit order (see Order), so a new encouragement never pushes out an earlier one. The `EncouragementDecoration` and `EncouragementKind` types are exported too.
- **Events:** `InsightAdded` v1 (`{ insightId, readingId, readerId, authorId }`) and `CongratulationAdded` v1 (`{ readingId, readerId, authorId }`, only when the congratulation was created, not on a repeat), published after commit, for notifications later. The tree does not subscribe to them: it reads the data on every request, so a lost event never loses a decoration.
- **Errors:** unknown reading, a reading of someone not followed, or (removing a congratulation) a reading that is not the own -> `404 reading_not_found`; own reading -> `409 cannot_encourage_own_reading`; insight on a finished reading -> `409 reading_finished`; congratulation on a reading in progress -> `409 reading_not_finished`; a fourth insight -> `409 insight_limit_reached`; unknown or foreign insight on delete -> `404 insight_not_found`; invalid input (text length, ids that are not UUIDs, page limits, invalid cursor) -> `400 validation_failed`. UUIDs in paths are accepted in any case and lower-cased.
- **Data:** `encouragements.insights` (`id` uuid primary key, `reading_id`, `reader_id`, `author_id` (all without FK), `text`, `created_at`; `insights_text_check`, `insights_not_own_check`, `insights_reading_id_created_at_id_idx` for the list and the decorations, `insights_author_id_reading_id_idx` for the limit and account deletion, `insights_reader_id_idx` for account deletion); `encouragements.congratulations` (`reading_id`, `author_id`, `reader_id` (without FK), `created_at`; primary key `(reading_id, author_id)`, `congratulations_not_own_check`, `congratulations_reading_id_created_at_author_id_idx`, `congratulations_author_id_idx`, `congratulations_reader_id_idx`).
- **Account deletion:** a `UserDeleted` v1 handler (`EraseEncouragementsHandler`) deletes, in one transaction through `retryOnDeadlock` (it deletes the rows other users wrote on the user's readings and the user's rows on theirs, so two erasures can cross), every insight and congratulation where the user is the author or the reader. Idempotent; a write admitted just before the deletion is erased by the delayed replay.
- **Follow-up:** notifications on `InsightAdded` and `CongratulationAdded`; a way for followers to find a finished reading without a review (e.g. a `BookFinished` card in the feed) so they can congratulate it; blocking; extracting the keyset cursor shared with the feed and reviews into platform code.

## Book search

Module `books`, `GET /v1/books?q=&limit=&offset=` (authenticated).

- **Normalising:** `books.search_normalise(text)` (`lower(unaccent(...))`, declared `IMMUTABLE` because `unaccent()` itself is only `STABLE` and cannot be indexed) normalises both the stored text and the query, always in SQL, so "stastie" finds "šťastie" and "kafka" finds "Kafka".
- **Matching:** the normalised query is split on whitespace into at most 5 distinct tokens; a work matches when every token is a substring (`LIKE`, wildcards `%`, `_`, `\` escaped) of its title, an edition title or an author name. A query that is an ISBN-13 or a valid ISBN-10 (hyphens and spaces ignored) also matches the edition with that `isbn13`.
- **Ranking:** best `word_similarity` of the whole query against the title, edition titles and author names first, then title, then id, so pages are stable.
- **Indexes:** GIN trigram expression indexes (`gin_trgm_ops`) on `books.search_normalise(...)` of `works.title`, `editions.title` and `authors.name` (`*_search_idx`), created in a migration. TypeORM does not load expression indexes, so they stay out of entity metadata and `db:migration:check`.
- **Input and answer:** `q` trimmed, 2 to 100 characters; `limit` 1 to 50 (default 20); `offset` 0 to 1000 (default 0). Answers `200` `{ items: [{ id, title, authors: [{ id, name }] }], nextOffset }`; `nextOffset` is `null` on the last page or when it would pass the offset limit.

## Media

Module `media`, Postgres schema `media`. Photos are uploaded through the backend, re-encoded and stored behind a storage port; nothing outside the storage adapter knows where the bytes live.

- **Storage port (Ports & Adapters):** `FILE_STORAGE` (`FileStorage`, `application/file-storage.ts`): `put(key, data, contentType)`, `read(key)` (`{ body, contentType, byteSize }` or `undefined`), `delete(key)` (idempotent) and `signedUrl(key, expiresAt)` (absolute URL). Keys are generated by the server only: `<mediaId>/<variant>.webp` (`mediaId` a server UUID).
- **Driver selection:** `MEDIA_STORAGE_DRIVER` (enum, only `local` for now, default `local`). `FileStorageModule.forConfiguredDriver()` maps each driver to its storage module (`STORAGE_MODULES`, a `Record` over the enum, so a new enum value does not type-check without its module); the module provides `FILE_STORAGE` through a factory provider from config. A driver is a module, not just a provider, because the local adapter brings its own controller.
- **Local adapter (now):** `storage/local/` - `LocalDiskStorage` writes under `MEDIA_LOCAL_ROOT` (default `./storage/media`, relative to the api working directory). Writes are atomic (temp file in the same directory, flushed, then renamed); every key is checked against the strict key pattern and the path is built from the real path of the root (`realpath` once), so no traversal. Symlinks are refused everywhere: the media directory must be a real directory (`lstat`), the file a regular file (`lstat`, then opened with `O_NOFOLLOW` and checked with `fstat`); a symlinked directory or file counts as missing (read -> `404`, delete -> no-op), logged at warn. `signedUrl` returns `${PUBLIC_API_URL}/v1/media/files/<key>?expires=<unix seconds>&signature=<HMAC-SHA256 of key and expiry with MEDIA_URL_SIGNING_SECRET, base64url>`. `GET /v1/media/files/*key` (`@Public()`, the signature is the authorisation, like an S3 presigned URL) verifies with a constant-time compare: invalid, missing or expired signature -> `403 invalid_media_signature`, a signed key without a file, or a key that is no stored variant (deleted media, also while its file deletion is still pending, or an orphan file) -> `404 media_file_not_found` (one lookup on the unique `file_variants_storage_key_key` index per file request, `STORED_MEDIA_KEYS`; the local module registers its own `TypeOrmStoredMediaKeyRepository`); success streams the file with `Content-Type: image/webp`, `X-Content-Type-Options: nosniff`, `Cache-Control: private, max-age=<seconds until expiry>`. The controller and the signature live only in `storage/local/`.
- **Local disk caveats:** the directory needs a persistent volume (docker compose mounts the named volume `libro-app-media` at `/app/apps/api/storage/media`) and backups; only one api instance can use it (no shared disk); files are served by the api process itself. `apps/api/storage/` is gitignored and not copied into images.
- **Adding S3 (AWS S3, DigitalOcean Spaces, Cloudflare R2, Hetzner):** add `'s3'` to `MEDIA_STORAGE_DRIVERS` (`src/config/media-storage-driver.ts`), its env variables (endpoint, region, bucket, access key, secret, path style) to `env.schema.ts` and `.env.example`, and `storage/s3/` with an `S3Storage implements FileStorage` (`signedUrl` = a presigned `GetObject` URL, `read` = `GetObject`) plus an `S3StorageModule` that provides `FILE_STORAGE` and register it in `STORAGE_MODULES`. It does not use the local controller or `MEDIA_URL_SIGNING_SECRET`. A presigned URL bypasses the stored-key check, so with S3 a file whose deletion is still pending stays reachable through URLs signed before the deletion until they expire (at most 1 hour). Nothing else changes; existing files are copied with their keys.
- **Upload:** `POST /v1/media` (authenticated) `multipart/form-data` with exactly one part, the file in field `file` (Nest `FileInterceptor`, multer memory storage, limits: file 10 MiB, 1 file, no other fields or parts). The original is never stored. `MediaUploadProblemsInterceptor` turns multer errors into our problems, so they never answer `500`.
- **Processing** (`SharpImageProcessor` behind `IMAGE_PROCESSOR`): the magic bytes must be JPEG, PNG or WebP and sharp must decode the same format (HEIC / AVIF, GIF, SVG, text, spoofed content types and broken files are refused); at most 50 megapixels (`limitInputPixels` plus a header check, against decompression bombs); only the first frame (no animation); EXIF orientation applied (`autoOrient`, the alias of `rotate()`); converted to sRGB and re-encoded to WebP (quality 82) with all metadata dropped (no EXIF, GPS, XMP, IPTC or ICC). Variants by the longer side, never enlarged: `small` 256 px, `medium` 1080 px, `large` 2048 px. The decoded image is first reduced to the `large` size, so memory per upload stays bounded.
- **Consistency:** the variants are written to storage first, then the rows are inserted in one transaction; if the insert fails (limit, database error), the written files are deleted best effort and failures are logged. Deleting (`DELETE /v1/media/:mediaId` and the `UserDeleted` erase) removes the rows and records every storage key in `media.pending_file_deletions` in the same transaction, then deletes the files (`MediaFileDeletionService`): a pending row is removed only after its storage delete succeeded; a failure increments `attempts`, records `last_error` (at most 1000 characters), is logged at warn and stays pending. After each deletion up to 10 other pending rows (fewest attempts, oldest first) are retried as well; the purge command (see [Account deletion](#account-deletion)) retries all of them (`MEDIA_FILE_DELETIONS.retryPending()`). So a crash or a storage failure never loses a file that must go. Never a `500` after the rows are gone.
- **Upload admission:** `MediaUploadAdmissionInterceptor` runs before `FileInterceptor` (interceptors run in listed order, after the auth guard), so a refused upload is answered before multer reads the body: `429 media_upload_busy` with `Retry-After: 1`. `UPLOAD_ADMISSION` (`InProcessUploadAdmission`) allows at most `MEDIA_UPLOAD_CONCURRENCY` uploads at once (env, default 4) and one per user. The permit is held through processing and storage writes and released exactly once when the request pipeline ends (success or error), or when the response closes before the body was complete (client abort). The limiter is in memory, fine for one instance; more instances need a shared limiter (Redis, later) behind the same port. A client abort maps to `400 validation_failed` (`errors[].code` `aborted`), never a logged `500`.
- **Limits:** at most 500 media per user (`MAX_MEDIA_PER_USER`): a cheap count before processing, then the authoritative check in the insert, under a transaction-scoped advisory lock per owner (`hashtextextended('media.files/' || owner_id)`), so concurrent uploads at the boundary never exceed it (also across instances later, where admission alone would not hold) -> `409 media_limit_reached`. Signed URLs are valid 1 hour (`MEDIA_URL_TTL_SECONDS`, a constant); every response signs fresh URLs and they all share `urlsExpireAt` (whole seconds).
- **Endpoints** (authenticated, owner only for now; another user's media answers `404 media_not_found` exactly like an unknown id): `POST /v1/media` (`201`), `GET /v1/media/:mediaId` (`200`) answer `{ id, width, height, createdAt, variants: { small, medium, large: { url, width, height } }, urlsExpireAt }` (`width` / `height` of the `large` variant); `DELETE /v1/media/:mediaId` (`204`).
- **Errors:** no file (or a non-multipart body) or a malformed multipart body (second file, extra fields) -> `400 validation_failed` (`errors[].path` `file`); over 10 MiB -> `413 media_too_large`; not JPEG / PNG / WebP or undecodable -> `415 unsupported_media_type`; over 50 megapixels -> `422 media_too_many_pixels`; at the per-user limit -> `409 media_limit_reached`; another upload of the same user running or `MEDIA_UPLOAD_CONCURRENCY` reached -> `429 media_upload_busy` (`Retry-After: 1`); unknown or foreign media -> `404 media_not_found`; signed file URLs as above.
- **Data:** `media.files` (`id` uuid primary key from the server, `owner_id` uuid without FK (the auth user id), `width`, `height` of the `large` variant, `created_at`; `files_owner_id_idx`) and `media.file_variants` (`file_id` -> `files` `ON DELETE CASCADE`, `name` CHECK `small` / `medium` / `large`, unique `storage_key`, `width`, `height`, `byte_size`; primary key `(file_id, name)`); `media.pending_file_deletions` (`storage_key` text primary key, `created_at`, `attempts` integer `>= 0`, `last_error` nullable; transient: a row lives only until its file is gone).
- **Public interface:** `MEDIA_LIBRARY` (`MediaLibrary`): `findOwned(userId, mediaId)` answers the media with signed variant URLs (`MediaWithUrls`) or `undefined`; `findMany(mediaIds)` answers a map of media id -> `MediaWithUrls` for the media that exist, whoever owns them (one query, unknown ids left out, URLs signed one media at a time; ids deduplicated, at most 100 distinct ids per call, `MAX_MEDIA_PER_CALL`, more throws a `RangeError`: a programmer error, chunk the ids), so the caller makes the authorisation decision: callers pass only media ids their owner attached themselves after a `findOwned` check (`profiles` the avatar, `feed` post photos, `reviews` the photo of a review) and show the URLs only inside answers the viewer may see; `feed` chunks a page's photo ids into calls of at most 100; `MediaNotFoundException` is exported too. The photo representation is shared from `index.ts` too: `MediaPhoto` / `toMediaPhoto` (domain), `mediaVariantsSchema` / `toMediaVariantsResponse`, `urlsExpireAtSchema(refreshedBy)` and `mediaPhotoFields(refreshedBy)` / `toMediaPhotoResponse` (HTTP); callers keep their own OpenAPI component ids (`PostPhoto`, `ReviewPhoto`, the avatar ids) on schemas built from these fields. `MEDIA_FILE_DELETIONS` (`MediaFileDeletions`): `retryPending()` retries every pending file deletion and answers `{ deleted, failed }`.
- **Env:** `MEDIA_STORAGE_DRIVER`, `MEDIA_LOCAL_ROOT`, `MEDIA_URL_SIGNING_SECRET` (at least 32 characters; production refuses blank and known non-secret values like `JWT_ACCESS_SECRET`, `src/config/non-secret-values.ts`), `PUBLIC_API_URL` (absolute http(s) URL, default `http://localhost:3000`, trailing slashes dropped), `MEDIA_UPLOAD_CONCURRENCY` (positive integer, default 4).
- **Tests:** the real `LocalDiskStorage` on a temporary directory per test file (`test/support/media-storage-per-file.setup.ts`), emptied before every media test; input images are generated with sharp inside the tests.
- **Follow-up:** cleanup of orphans (media no post, review or profile uses, e.g. after the post was deleted, and files without rows after a crash between write and insert; deleting a photo already leaves it out of every post, review and avatar); moderation; the S3 adapter, then presigned direct uploads from the app with processing in a queue (BullMQ) instead of in the request.

## Profiles

Module `profiles`, Postgres schema `profiles`. The public face of a user (handle, display name, bio, favourite genres, top 3 books, avatar) and the follow graph. Reading data, trees and the forest stay private; profiles do not expose them.

- **Visibility and following:** every profile is visible to every authenticated user. Following is one-way and needs no approval (like a public Instagram account).
- **Creation:** a `UserRegistered` v1 handler creates the profile with a generated handle (`INSERT ... ON CONFLICT (user_id) DO NOTHING`, idempotent). Events can be lost, so `GET` / `PATCH /v1/me/profile` and following create a missing profile of the signed-in user the same way. Profiles are never created for other ids: another user without a profile answers `404 profile_not_found` and cannot be followed.
- **Default handle:** `citatel` + 6 random digits (`HANDLE_SUFFIX_SOURCE`, `crypto.randomInt`); a taken one (unique violation of `profiles_handle_key`) is retried with new digits: 3 attempts with 6 digits, then 3 with 12, then the request answers `503 profile_provisioning_unavailable` with `Retry-After: 1` (practically never; logged at warn). Tests replace only the digit source.
- **Handle:** trimmed and lower-cased, then 3 to 30 characters: letters `a-z` and digits joined by single dots or underscores (`^[a-z0-9]+([._][a-z0-9]+)*$`, so no dot or underscore at the start or end and never two in a row). Stored lower case, so uniqueness and lookups ignore case; the rule is also a CHECK (`profiles_handle_check`). A taken handle answers `409 handle_taken`, also for concurrent changes (the unique violation is mapped in the repository).
- **Display name and bio:** NFC-normalised and trimmed; display name at most 50, bio at most 300 characters (Unicode code points); blank or `null` stores `NULL`. `char_length` CHECKs back it up.
- **Favourite genres:** at most 10 distinct keys from the fixed list `GENRES` (`domain/genres.ts`, stable snake_case keys the app translates; `GET /v1/profiles/genres`), in the given order. Stored as a `text[]` column of the profile (`profiles_favourite_genres_check` caps it at 10): the list is always read and written whole and later matching can index it with GIN. Keys are validated in code, not by a CHECK, so adding a genre needs no migration; keys no longer in the list are left out of answers.
- **Top books:** 0 to 3 distinct work ids, best first (`profiles.top_books`, `position` 1 to 3). Every id must be in the catalogue (`BOOK_CATALOGUE.findWorkSummaries`, one batch call), else `404 book_not_found` and nothing changes. Answers show `{ id, title, authors }` from the same batch call; a work no longer in the catalogue is left out.
- **Avatar:** `avatarMediaId` must be a photo of the user (`MEDIA_LIBRARY.findOwned`), else `404 media_not_found`; `null` removes it. Answers sign the URLs with `MEDIA_LIBRARY.findMany`, so other users see the avatar too; a deleted photo answers `avatar: null`, never an error. The media id is kept without FK.
- **Partial update:** `PATCH /v1/me/profile` changes only the fields present; `null` clears a nullable field. Top books and avatar are checked first, then one transaction updates the profile row (which locks it, so concurrent updates of the top books are serialised) and replaces the top books when sent.
- **Following:** `PUT` follows and `DELETE` unfollows, both idempotent (`204` whether or not something changed). The own profile answers `409 cannot_follow_self` for both (a rule about the state, not malformed input; `follows_not_self_check` backs it), an unknown target or one without a profile `404 profile_not_found`. A user follows at most 2000 profiles (`MAX_FOLLOWING`), so following lists and `followeeIdsOf` stay bounded: a follow is one transaction under a transaction-scoped advisory lock per follower (`hashtextextended('profiles.follows/' || follower_id)`) that checks for an existing follow, locks the followee row (`FOR KEY SHARE`) and counts, so concurrent follows never pass the cap -> `409 follow_limit_reached`. An existing follow still answers `204` at the cap. Followers are not capped.
- **Search:** like book search: `profiles.search_normalise(text)` (the module's own `lower(unaccent(...))`, `IMMUTABLE`; a module never calls another module's database objects) on both sides, at most 5 distinct whitespace tokens, a leading `@` of a token ignored, every token a substring (`LIKE`, wildcards escaped) of the handle or the display name; ranked by the best `word_similarity` against handle or display name, then handle, then user id. GIN trigram expression indexes `profiles_handle_search_idx` and `profiles_display_name_search_idx`, created in the migration (TypeORM ignores expression indexes).
- **Official accounts (LIB-34):** `profiles.profiles.official` (boolean NOT NULL DEFAULT `false`, partial index `profiles_official_idx` on `user_id` WHERE `official`) marks the accounts of the Libro team; their posts are the Libro announcements of the feed (see [Feed](#feed)) and the app shows a badge (`official` in profiles and summaries). Never set through the API (`PATCH /v1/me/profile` ignores it): only by the CLI `pnpm profiles:set-official <handle>` and `pnpm profiles:set-official <handle> --revoke` (root alias of `pnpm --filter @libro/api run profiles:set-official`; `src/cli/set-official-account.ts`, a Nest application context running `runOfficialAccountCommand` from `src/cli/official-account-command.ts` with `OFFICIAL_ACCOUNTS`). The handle is normalised like everywhere (a leading `@` is dropped). It logs the outcome; an unknown handle (`No profile has the handle @...`), a grant over the cap or a wrong usage exits with code 1; setting the current state again changes nothing and exits 0. At most 20 official accounts (`MAX_OFFICIAL_ACCOUNTS`): a grant is one transaction under a transaction-scoped advisory lock (`hashtextextended('profiles.official', 0)`) that locks the profile row, counts and updates, so concurrent grants never pass the cap. The team writes announcements as normal posts of the official account in the app; there are no admin endpoints.
- **Queries:** a profile costs one query (row, top book ids, follower and following counts, `followedByMe`) plus one catalogue and one media call; a page of summaries one query plus one media call, whatever its size.
- **Endpoints** (all authenticated): `GET /v1/me/profile` and `PATCH /v1/me/profile` (`{ handle?, displayName?, bio?, favouriteGenres?, topBookIds?, avatarMediaId? }`) answer the own profile; `GET /v1/profiles/:userId` and `GET /v1/profiles/by-handle/:handle` a profile; `GET /v1/profiles?q=&limit=&offset=` (`q` trimmed, 2 to 50 characters), `GET /v1/profiles/:userId/followers` and `/following` (most recent follow first) answer `{ items: [summary], nextOffset }` with `limit` 1 to 50 (default 20) and `offset` 0 to 1000 (default 0), `nextOffset` as in book search; `PUT` / `DELETE /v1/profiles/:userId/follow` answer `204`; `GET /v1/profiles/genres` answers `{ genres }`. A profile is `{ userId, handle, displayName, bio, favouriteGenres, topBooks: [{ id, title, authors: [{ id, name }] }], avatar, official, followerCount, followingCount, followedByMe }`, a summary `{ userId, handle, displayName, avatar, official, followedByMe }` (`official` was added in LIB-34, additively, in every copy of the summary: profiles, feed, reviews, live sessions, encouragements), `avatar` is `{ variants: { small, medium, large: { url, width, height } }, urlsExpireAt }` or `null`. `followedByMe` is about the signed-in user (`false` on the own profile). UUIDs in paths and bodies are accepted in any case and lower-cased.
- **Errors:** unknown user, user without a profile or unknown handle -> `404 profile_not_found`; taken handle -> `409 handle_taken`; unknown top book -> `404 book_not_found`; avatar that is not an own photo -> `404 media_not_found`; following or unfollowing yourself -> `409 cannot_follow_self`; following more than 2000 -> `409 follow_limit_reached`; no free default handle -> `503 profile_provisioning_unavailable` (`Retry-After: 1`); invalid input (handle rule, lengths, unknown or repeated genre, more than 10 genres, more than 3 or repeated books, ids that are not UUIDs, search and page limits) -> `400 validation_failed`.
- **Data:** `profiles.profiles` (`user_id` uuid primary key, the auth user id without FK; `handle` (`profiles_handle_key`); `display_name`; `bio`; `favourite_genres` `text[]`; `avatar_media_id` uuid without FK; `official` boolean (`profiles_official_idx`); `created_at`, `updated_at`); `profiles.top_books` (`user_id` -> `profiles` `ON DELETE CASCADE`, `position`, `work_id` without FK; primary key `(user_id, position)`, unique `top_books_user_id_work_id_key`); `profiles.follows` (`follower_id`, `followee_id` -> `profiles` `ON DELETE CASCADE`, `created_at`; primary key `(follower_id, followee_id)`, `follows_not_self_check`, `follows_followee_id_created_at_idx`).
- **Public interface:** `SOCIAL_GRAPH` (`SocialGraph`): `isFollowing(followerId, followeeId)` and `followeeIdsOf(userId)` (most recent follow first, at most 2000); `PROFILE_DIRECTORY` (`ProfileDirectory`): `findSummaries(viewerId, userIds)` answers a map of user id -> summary (`followedByMe` for the viewer, unknown ids left out, one query plus one media call); ids are deduplicated and at most 100 distinct ids per call are allowed (`MAX_PROFILE_SUMMARIES_PER_CALL`, more throws a `RangeError`: a programmer error, chunk the ids). `officialUserIds()` answers the user ids of the official accounts (one query on `profiles_official_idx`, at most `MAX_OFFICIAL_ACCOUNTS`). `OFFICIAL_ACCOUNTS` (`OfficialAccounts`, for the CLI only): `grant(handle)` and `revoke(handle)` answer `changed` | `unchanged` | `profile_not_found` | `limit_reached`. `ProfileNotFoundException`, `MAX_OFFICIAL_ACCOUNTS` and the `ProfileSummary`, `Avatar` and `OfficialAccountChange` types are exported too. Profiles use `BOOK_CATALOGUE.findWorkSummaries(workIds)` (map of work id -> `{ id, title, authors }` for the works in the catalogue; deduplicated, at most 100 distinct ids per call, `MAX_WORK_SUMMARIES_PER_CALL`, more throws a `RangeError`) from the books public interface.
- **Follow-up:** blocking and muting; private profiles with follow requests; sharing the forest and trees with followers; reserved handles (e.g. `admin`, `libro`).

## Feed

Module `feed`, Postgres schema `feed`. Readers share short posts (optionally about a book and a place, with up to 4 photos), like them and react with emoji. Posts contain only what the author wrote: no reading data, trees or sessions leak into the feed.

- **Visibility:** every post is visible to every authenticated user (the community feed). Two tabs: `following` (the own posts plus those of the profiles the viewer follows) and `community` (everyone).
- **Post:** `text` NFC-normalised and trimmed, at most 2000 characters (Unicode code points); a post needs text or at least one photo (neither -> `400 validation_failed`, `errors[].path` `text` with the codes from before photos: `invalid_type` for a missing or `null` text, `too_small` for a blank one), so with a photo `text` may be left out, `null` or blank and stores `NULL`; `workId` optional, must be in the catalogue (`BOOK_CATALOGUE.workExists`, else `404 book_not_found`); `place` optional free text like a reading session place, NFC-normalised and trimmed, at most 100 code points, blank or `null` stores `NULL`. Posts cannot be edited. `char_length` CHECKs back both lengths up.
- **Reactions instead of comments:** no text comments. A reaction is one of a fixed set, identified by a stable ASCII key used in URLs and storage: `heart` ❤️, `books` 📚, `clap` 👏, `wow` 😮, `laugh` 😂, `hug` 🤗, `thinking` 🤔 (`REACTIONS`, `domain/reactions.ts`; `GET /v1/feed/reactions` lists them in display order). A reader adds each reaction at most once per post (several different ones are fine). The emoji themselves are not accepted in paths (only the keys); responses carry both `key` and `emoji`. Adding a reaction is a code change plus a migration of `reactions_reaction_check`; a key is never renamed or removed while it is stored.
- **Likes and reactions** are idempotent: `PUT` adds and `DELETE` removes, both `204` whether or not something changed; an unknown post answers `404 post_not_found`. Adding locks the post row (`FOR KEY SHARE`) in the same statement, so a like racing a post deletion answers `404`, never a foreign key `500`. Likes and reactions are public counts; who liked is not exposed, who reacted is (`GET /v1/posts/:postId/reactions`).
- **Deleting:** only the author deletes a post; another user's post answers `404 post_not_found` exactly like an unknown one (no `403`, consistent with the other modules). Likes and reactions cascade with it.
- **Spam limit:** at most 30 posts per author in a rolling 24 hours (`POST_LIMIT`), otherwise `429 post_limit_reached` with `Retry-After` (seconds until the 30th newest post in the window is a day old, at least 1). The check is the insert itself (`INSERT ... SELECT ... WHERE (count in the window) < 30`) under a transaction-scoped advisory lock per author (`hashtextextended('feed.posts/' || author_id)`), and the database clock is sampled once after the lock (`clock_timestamp()`) and passed to the count, the insert's `created_at` and the `Retry-After` computation, so concurrent posts never pass the limit and the window is a fixed bound on `posts_author_id_created_at_id_idx`. A deleted post no longer counts.
- **Pagination (keyset):** feeds, a user's posts and the reactions of a post are ordered newest first by `(created_at, id)` descending and paged with an opaque `cursor` (`nextCursor` of the previous page, base64url JSON of `created_at` with microseconds and the id; `null` on the last page). `limit` 1 to 50 (default 20). An invalid cursor (characters outside the base64url alphabet, padding or a non-canonical encoding, not JSON, unknown fields, not a calendar time, not a UUID) answers `400 validation_failed` (`errors[].path` `cursor`). Posts with the same time are ordered by id, so pages never repeat or skip a post, also when new posts arrive between pages. The cursor keeps microseconds (`to_char(... 'US')` in SQL), so posts within the same millisecond page correctly.
- **Following feed:** `SOCIAL_GRAPH.followeeIdsOf(viewer)` (at most 2000, the follow cap) plus the viewer, then one query with `author_id = ANY($ids)`.
- **Queries:** a page costs the same bounded number of queries whatever its size: one for the posts with their like count, `likedByMe` and reaction counts (correlated subqueries per row, the page is at most 50 rows), one `PROFILE_DIRECTORY.findSummaries` call (plus its media call when an author has an avatar), one `BOOK_CATALOGUE.findWorkSummaries` call, `MEDIA_LIBRARY.findMany` calls for the photo ids (read with the posts as an ordered array per row; none without photos), and for the following feed one `followeeIdsOf`. A page has at most 50 distinct authors and works, under the 100-id maxima of those interfaces, but up to 200 photos: they are chunked into calls of at most 100 ids, so at most 2 media calls.
- **Missing references:** an author (or reacting reader) without a profile is shown with `author: null` (`user: null`) next to the always present `authorId` (`userId`); this happens only after a lost `UserRegistered` event (posts of deleted accounts are erased, see Account deletion). A work no longer in the catalogue shows `book: null`.
- **Photos:** `photoIds` lists 0 to 4 distinct media ids (any case, lower-cased) in the order to show; every one must be a photo of the author (`MEDIA_LIBRARY.findOwned`, one call per id, at most 4), else `404 media_not_found` and nothing is stored. The post and its photo links are inserted in one transaction. Answers show `photos` in that order, signed with `MEDIA_LIBRARY.findMany`; a deleted photo is left out, never an error (a photo-only post whose photos were all deleted shows `text: ""` and `photos: []`). Photos are visible to everyone who sees the post. Deleting a post removes its photo links, not the photos (orphans, see Media follow-up). Before LIB-33 `text` was required and `photos` always `[]`; optional text and filled photos are additive: `text` stays a string in answers (`""` for a post without text), so old apps keep working. Reverting the photos migration keeps every post with its likes and reactions: a post without text gets the text `📷`.
- **Endpoints** (all authenticated): `POST /v1/posts` (`{ text?, workId?, place?, photoIds? }`, `201`); `GET /v1/posts/:postId` (`200`); `DELETE /v1/posts/:postId` (`204`); `GET /v1/posts?authorId=&cursor=&limit=` (posts of one user, an unknown user answers an empty page); `PUT` / `DELETE /v1/posts/:postId/like` (`204`); `PUT` / `DELETE /v1/posts/:postId/reactions/:reaction` (`204`); `GET /v1/posts/:postId/reactions?cursor=&limit=` answers `{ items: [{ userId, user, key, emoji, createdAt }], nextCursor }`; `GET /v1/feed/following` and `GET /v1/feed/community` (`?cursor=&limit=`) answer `{ items: [post], nextCursor }`; `GET /v1/feed/reactions` answers `{ reactions: [{ key, emoji }] }`. A post is `{ id, authorId, author, text, book: { id, title, authors: [{ id, name }] } | null, place, createdAt, likeCount, likedByMe, reactions: [{ key, emoji, count, reactedByMe }], photos: [{ mediaId, width, height, variants: { small, medium, large: { url, width, height } }, urlsExpireAt }] }` (`width` / `height` of the `large` variant); `author` / `user` is a profile summary `{ userId, handle, displayName, avatar, official, followedByMe }` or `null`; `reactions` lists only the used ones, in display order. UUIDs in paths and queries are accepted in any case and lower-cased.
- **Errors:** unknown post, or deleting another user's post -> `404 post_not_found`; unknown book -> `404 book_not_found`; a photo that is not an own photo -> `404 media_not_found`; over 30 posts in 24 hours -> `429 post_limit_reached` (`Retry-After`); invalid input (text or place lengths, neither text nor photo, more than 4 or repeated photos, ids that are not UUIDs, unknown reaction keys, page limits, invalid cursor) -> `400 validation_failed`.
- **Data:** `feed.posts` (`id` uuid primary key, `author_id` uuid without FK (the auth user id), `text` (nullable, a post with photos only), `work_id` uuid without FK, `place`, `created_at`; `posts_text_check`, `posts_place_check`, `posts_created_at_id_idx` for the community feed and `posts_author_id_created_at_id_idx` for the following feed, a user's posts and the limit; both are read backwards for newest first); `feed.post_photos` (`post_id` -> `posts` `ON DELETE CASCADE`, `position` 1 to 4 (`post_photos_position_check`), `media_id` uuid without FK; primary key `(post_id, position)`, unique `post_photos_post_id_media_id_key`); `feed.likes` (`post_id` -> `posts` `ON DELETE CASCADE`, `user_id` without FK, `created_at`; primary key `(post_id, user_id)`, `likes_user_id_idx` for account deletion); `feed.reactions` (`id`, `post_id` -> `posts` `ON DELETE CASCADE`, `user_id` without FK, `reaction` key (`reactions_reaction_check`), `created_at`; unique `reactions_post_id_user_id_reaction_key`, `reactions_post_id_created_at_id_idx`, `reactions_user_id_idx` for account deletion).
- **Events:** `PostCreated` v1 (`{ postId, authorId }`), published after commit (for notifications later). No public interface yet.
- **Activity feed (LIB-34):** the app shows three tabs: Libro announcements, book updates ("X started reading BOOK", "X finished BOOK" with the rating and review) and statuses (the posts, as in `following` / `community`). The backend serves them as filters of one endpoint, so the app can merge or reorder tabs without backend changes; `GET /v1/feed/following` and `/community` stay exactly as they were.
  - **Timeline:** `feed.activities` (`id` uuid primary key from the server, `actor_id` uuid without FK (the user who did it), `kind` text CHECK `post` | `reading_started` | `book_finished` (`activities_kind_check`), `post_id` uuid nullable -> `posts` `ON DELETE CASCADE` (unique `activities_post_id_key`), `reading_id` and `work_id` uuid nullable without FK (ids of `reading-sessions` and `books`), `created_at`; `activities_shape_check`: a `post` has only `post_id`, a reading kind has `reading_id` and `work_id` and no `post_id`; unique `activities_kind_reading_id_key` so a replayed event never duplicates; `activities_actor_id_created_at_id_idx` and `activities_created_at_id_idx`). Creating a post inserts its `post` activity in the same transaction with the same `created_at` (the post factory does the same through a cascade); deleting the post cascades it; the migration backfilled one for every existing post. `RecordReadingActivityHandler` turns `ReadingStarted` v1 into `reading_started` and `BookFinished` v1 into `book_finished` (actor = `userId`, `created_at` from `clock_timestamp()` at insert, `INSERT ... ON CONFLICT (kind, reading_id) DO NOTHING`). Activities hold ids only, never reading data beyond the book.
  - **Endpoint:** `GET /v1/feed/activity?tab=following|community&type=all|announcements|reading|posts&cursor=&limit=` (authenticated; `tab` default `following`, `type` default `all`; `limit` 1 to 50, default 20; keyset by `(created_at, id)` of the activity exactly like the post feeds, an invalid cursor, tab or type -> `400 validation_failed`) answers `{ items: [{ id, kind, actorId, actor, createdAt, post, reading }], nextCursor }`: `actor` a profile summary or `null`, `post` exactly the post shape above for a `post` activity (else `null`), `reading` `{ readingId, book: { id, title, authors } | null, review: { rating, text, photo } | null }` for the reading kinds (else `null`; `readingId` lets followers add an insight or a congratulation, see [Encouragements](#encouragements); `review` only on `book_finished`, when the reader reviewed that reading; `photo` has the review / post photo shape or `null`). A post activity whose post was deleted between the two queries is left out of the page. The app ignores unknown kinds, so a new kind is additive.
  - **Visibility (one SQL predicate, `TypeOrmFeedTimelineRepository`):** `posts` = `post` activities of today's audience (tab `following`: the viewer plus `SOCIAL_GRAPH.followeeIdsOf`; tab `community`: everyone); `announcements` = `post` activities of official accounts (`PROFILE_DIRECTORY.officialUserIds()`), for every viewer whatever the tab and following; `reading` = `reading_started` / `book_finished` of the viewer and of followees that share their reading activity (`READING_ACTIVITY_SHARING.sharingWithFollowers`), whatever the tab, never of strangers and never through the community audience (reading data is private); `all` = the union, each activity once. `ActivityAudienceService` builds a `TimelineAudience` (`everyonesPosts`, `postAuthorIds`, `readingActorIds`) from the tab and the type (`SOURCES_OF_TYPE`); sharing is checked on every read, so `readingActivity: nobody` hides older activities at once and `followers` shows them again.
  - **Hydration (Strategy):** `ACTIVITY_HYDRATORS` is a `Record<ActivityKind, ActivityHydrator>` (so a new kind does not type-check without its strategy): `PostActivityHydrator` (one `PostRepository.findMany` with likes, reactions and photo ids, then the shared post assembly), `ReadingStartedHydrator` (no query) and `BookFinishedHydrator` (one `READING_REVIEWS.findForReadings`). Each strategy plans a whole page (`HydrationPlan`: the profile, work and media ids it needs plus a `detailsOf` builder); `ActivityFeedService` merges the ids and resolves them once through `FeedReferencesService` (also used by `PostAssemblerService`). Adding a kind = an enum value, a CHECK migration and a strategy; the core does not change.
  - **Queries:** a page costs the same bounded number whatever its size and only what the type needs: at most one `followeeIdsOf`, one `officialUserIds` (not for tab `community`, whose posts already include them), one `sharingWithFollowers` (only for reading activity, none without followees), one activities query, one posts query, one reviews query (only with `book_finished` items), one `findSummaries` (actors and post authors, at most 50), one `findWorkSummaries` (at most 50) and media calls chunked to 100 ids (post and review photos).
  - **Scaling:** reads are fan-out-on-read over two indexes; the read side is behind `FEED_TIMELINE` (`FeedTimeline`: `page(audience, query)`, `recordReading(activity)`), so a later switch to fan-out-on-write (per-viewer inboxes, a queue) does not change the API or other modules.
- **Account deletion:** a `UserDeleted` v1 handler (`EraseFeedDataHandler`, `FEED_ERASURE_REPOSITORY`) deletes, in one transaction under the per-author advisory lock (`feed.posts/<user id>`, so a post being created commits before or after it), the user's likes and reactions on any post, the user's activities (`actor_id`), then the user's posts (likes and reactions of others on them, their photo links and post activities cascade; the photos themselves are erased by `media`). Idempotent: a replay deletes nothing more. Other users' posts stay, only without the deleted user's likes and reactions.
- **Follow-up:** reporting and moderation of posts and their photos; blocking and muting in the feeds; notifications on `PostCreated`, likes and reactions; editing posts; a shared rate limit store if the per-author advisory lock is not enough across instances.

## Database rules

- PostgreSQL only. Schema per module: entities declare `schema: '<module>'`, the module's first migration creates the schema (`queryRunner.createSchema('<module>', true)`) and its `down()` drops it (`queryRunner.dropSchema('<module>')`).
- Schema changes go **only through migrations** (TypeORM CLI, `up()` + `down()`). Data migrations live in `up()` too. Migrations live in a `migrations/` folder (`pnpm db:migration:generate <Name>` writes to `apps/api/src/database/migrations/`).
- `synchronize` is always `false`, in every environment, including local. CI fails when an entity changes without a migration (`pnpm db:migration:check`).
- Extensions are enabled only in migrations, in the `public` schema. TypeORM's `installExtensions` stays off.
- Use foreign keys, unique constraints and `ON DELETE` rules inside a module so integrity (and GDPR deletion) is enforced by the database, not by hope.
- Use JSONB for genuinely flexible data, not as a way to skip modelling.
- Seeders / factories via `typeorm-extension`.
- Host in the EU (e.g. Neon or Supabase, Frankfurt). Locally and in tests: Docker `postgis/postgis`.

## API versioning

Mobile users do not update immediately, so old app versions must keep working.

1. **Backward-compatible changes by default.** Adding fields, optional params and new endpoints needs no new version. Removing / renaming a field, changing its type or meaning, or adding a required param is breaking and needs a new version.
2. **URI versioning from day one:** `app.enableVersioning({ type: VersioningType.URI, defaultVersion: '1' })`, routes under `/v1/...`. Version only the endpoints that changed (`@Version('2')` or a `V2` controller).
3. **Minimum supported app version.** The app sends `X-App-Version` and `X-Platform` on every request. The backend keeps a per-platform minimum and answers older clients with `426 Upgrade Required`; the app then shows a forced-update screen.
   - `X-Platform` is `ios` or `android`, `X-App-Version` is `MAJOR.MINOR.PATCH`; minimums come from `MIN_APP_VERSION_IOS` / `MIN_APP_VERSION_ANDROID` (default `0.0.0`).
   - Neither header: the request passes (health checks, curl, web). Both valid and below the minimum: `426` with code `app_update_required`. Only one header, unknown platform or malformed version: `400` with code `invalid_app_client`.
   - Every request with app headers that reaches a route logs one `client platform=... version=... outcome=...` line, so usage of old versions can be counted. Requests without them are not logged.
4. **Expo OTA (EAS Update)** for JS-only changes; native changes still need a store release and must match `runtimeVersion`.
5. **Deprecation:** keep an old API version for 3-6 months, track usage by `X-App-Version`, remove it only when unused or below the minimum supported version.
6. The app must tolerate unknown fields and unknown enum values (ignore or show a fallback, never crash).
7. **Contract tests** assert that `v1` response shapes stay unchanged.

## API input and errors

- **Every input has a zod schema:** body, query and params are declared with `@Body({ schema })`, `@Query({ schema })`, `@Param({ schema })`. A parameter without a schema is not validated.
- **Unknown request fields are stripped,** not rejected (`z.object`). Use `z.strictObject` only where rejecting is a deliberate part of the contract.
- **No NUL characters:** PostgreSQL cannot store U+0000 in text, so the global validation pipe (`TextSafeValidationPipe`, `src/http/validation/`) rejects every validated body, query or params value that still contains one after its schema passed, at any depth: `400 validation_failed` with one `errors[]` entry per string (`path` like `editions.0.title`, `code` `invalid_format`). New schemas get it for free; do not repeat the check in modules.
- **Every error is RFC 9457 Problem Details** (`application/problem+json`: `type`, `title`, `status`, `detail`, `instance`, `code`, plus `errors[]` with `path`, `message`, `code` for validation). Only the global `ProblemDetailsFilter` writes error responses. Clients branch on `code`, never on `detail`. The one exception is `/health`, which answers `503` with its own health report (same shape as its `200`).
- Throw `ProblemException` with an own `code` for domain errors; plain Nest `HttpException`s get a code derived from the status (`not_found`, `conflict`, ...). 5xx never expose internal messages; they are logged server-side.
- The error shape is part of the `v1` contract: changing it needs a new version.

## Testing

- Feature / integration tests through real collaborators against a **real PostgreSQL** (Testcontainers). Do not mock internal repositories, services or helpers.
- Integration tests use the harness in `apps/api/test/support/` (`test` from `integration-test.ts`): one Testcontainers Postgres per run, a database per test file cloned from the migrated template, tables truncated before every test. Tests and test files must not depend on each other or on their order.
- Mock / stub only true external boundaries (Stripe, object storage, third-party HTTP APIs). Never make real network calls to third parties in tests.
- Never `throw` in test code; use the framework's assertions so a failed precondition reads as an assertion failure.
- Verify changes with **lint, typecheck (`tsc --noEmit`) and tests**. Do not run a production build just to check that code compiles.

## Code style

- SOLID throughout; depend on abstractions so units are testable and swappable.
- Use design patterns where they genuinely fit (Strategy, Repository, Factory, Adapter, Command, Observer, Pipeline, ...). Do not force them.
- Guard clauses / early return. No `else` / `else if`.
- Small, focused classes and functions.
- No code comments unless explicitly requested. Only tooling-required annotations are allowed, without prose.
- In prose (docs, PR / commit messages) use a plain hyphen `-`, never long dashes.

## Git

- Branch name: use the branch name Linear generates for the issue (`<user>/lib-<n>-<slug>`, "Copy git branch name" in the issue). The `lib-<n>` part links the PR to the issue.
